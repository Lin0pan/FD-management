## Codebase Patterns
- **Adding a `DomainErrorCode` is a three-file change**: the union in `src/domain/errors.ts`, the
  class beside it, and `TIERS` in `src/app/notice-tier.ts`. `TIERS` is a `Record` over the union, so
  the *build* fails until the code is tiered — that is the mechanism, not an obstacle. The header
  comment of `notice-tier.ts` counts the codes ("a 32nd code…", "the six red ones"), so it goes
  stale silently; update it with the entry.
- **The same mechanism guards `SettingsChange`**: its `switch` in `src/app/einstellungen/page.tsx`
  is exhaustive with no `default`, so adding a member to the union fails the build until the screen
  renders it. Do not silence it with a `default` branch.
- **An error class with no caller yet still needs a test**, because `domain/` coverage is gated at
  100%. `src/domain/errors.test.ts` is where those live — see the `MissingAuditReason` block for the
  shape, including the comment saying which story will call it.
- **`errors.ts` cannot import from `domain/card/`**: `cardNumber.ts` imports `errors.ts`, so a
  message that wants to read `66k1` writes the `k` inline rather than calling `formatCardNumber`.
- **Adding a field to `Settings` is a wide change before it is a deep one.** `createSettings` is
  called from the repository, the seed, the settings server action and every hand-written fake in
  the application tests; all of them must supply the new field before anything compiles. Land the
  field with a placeholder value at each call site, then replace them in the story that owns each.
  Get the *files* out of a wide break rather than the errors:
  `npm run typecheck 2>&1 | grep -E "^src/" | cut -d'(' -f1 | sort -u`.
- **A test that merely *uses* a field is not a test *of* it.** Several `settings.test.ts` cases
  reach for an arbitrary second field to prove the same-instant tie rule or the audit's changed-field
  list. When that field goes away, **re-point them**, do not delete them — deleting takes an
  unrelated rule with it and drops coverage below the gate.
- **A Prisma `P2002` cannot always name *which* constraint was broken.** `meta` is
  `{ modelName, target: [columns] }`, but where two unique indexes both cover the offending row
  SQLite reports only one of them, and not the one that was declared or created first. Where the
  distinction matters, match the target for the *shape* and then ask the database the question that
  actually distinguishes the two faults (`card-repository.ts`'s `issue` counts the customer's own
  rows on that index). For a **nested** write Prisma reports the *rooted* model — a card refused
  inside `customer.create` comes back as `modelName: "Customer"` — so the model name alone tells
  nothing about which table failed.
- **Regenerating `prisma/migrations/` drops the hand-written partial unique index** on
  `Customer.customerNumber` (`Customer_customerNumber_onRegister_key`) at the end of the migration
  SQL. `src/infrastructure/prisma/schema.test.ts` greps for it and for the `onDelete: Restrict`
  clauses, so a lost line fails CI rather than production — but re-add it deliberately. Three things
  batches 25–27 each had to learn:
  - **Delete `data/fd.db` before `migrate dev`**: with the old migration row still in
    `_prisma_migrations`, Prisma refuses to regenerate and writes nothing.
  - **Verify with `diff`, not by reading the new file**:
    `git show HEAD:prisma/migrations/<old>/migration.sql > /tmp/old.sql && diff /tmp/old.sql <new>`
    states in a few lines what the story is allowed to have changed. Anything else is a Prisma
    version drifting the DDL under you, which no gate would attribute to this commit.
  - **`migrate dev` applies the migration *before* the hand-written index is appended**, so the
    database it leaves does not have the index even though the committed SQL does. `npm run db:reset`
    afterwards is what makes the two agree — check with
    `SELECT sql FROM sqlite_master WHERE name='Customer_customerNumber_onRegister_key'` rather than
    trusting that the reset ran.
  - A regeneration **renames a directory that documents cite by name**. `grep -rn "<old-timestamp>_init"
    docs/ src/ tests/` afterwards; prefer the `prisma/migrations/*_init/migration.sql` glob, which
    survives the next one.
- **Never `pkill -f "next dev"`, and never `pkill -f "node.*next-server"`** — both patterns match the
  Bash tool's own wrapper command line and kill the shell (exit 144, no output). **And `ss` is not
  installed in this sandbox**, so `ss -ltnp | grep :3000 || echo free` reports "free" for every port,
  always: the `||` fires on `command not found`. (Batch 27's per-story notes recommend `ss` in two
  places — they are wrong; that is the bug this bullet exists to stop.) Check
  `ps aux | grep "[n]ext-server"` — the bracket keeps the pattern out of its own match — and
  `kill <pid>` by number.
- **A stale `next start` from an earlier iteration silently serves a mixed build.** The new
  `npm run start` fails with `EADDRINUSE` in the background while the page still renders, from the
  old server reading the *new* chunks off disk — a couple of console 500s are the only symptom.
  Check for a live server (`ps`, above) **before** trusting any browser check.
- **`npm run db:reset` does not reach a server that is already running.** It deletes `data/fd.db`,
  and SQLite keeps serving the running process from the deleted inode, so the screen goes on showing
  the pre-reset data. Restart the server after a reset, or the verification is of the old database.
  `db:seed` fills settings only — customers are not seeded, so a reset empties whatever manual
  clicking built up (the e2e suite makes its own registers).
- **Changing a seeded policy value moves e2e expectations.** `grep -rn ',00 €' tests/e2e/` before
  editing a number in `seed.ts`.
- **The e2e customer-number bands, as they now stand.** Below the quota of 240: counter 201–206 and
  239, allowance 211, serve 221–222, reminders 231, registration 232–234, card numbers 236. Above it:
  block 241, reissue 251, age-13 271, customer-list 281–285, customer-record 291–293, group-progress
  301–303, group-walk 311–315, price cap 321, eggs 331–334, balance 341–344. A spec whose number must
  be **pickable in the /kunden/neu dropdown** has to sit below 240 — the pool is `1..quotaN` — and
  everything else should stay above it, clear of the low sequence the allocating specs (registration,
  card, archive, reregistration) consume. **A new spec takes a new band**; do not borrow another
  spec's numbers. **And a band above 315 must be seeded BLUE**: `group-walk.spec.ts` reads the whole
  shared register and asserts that the highest walkable RED number *is* its own 315, so one RED
  household seeded higher fails a spec the new one has no business in — `eggs` and `balance` are both
  BLUE for that reason and not by taste. **Below 240 the band may be RED**, which is what lets a spec
  reuse the RED distribution Thursday `2026-01-08` the reissue and card-number specs already pin —
  `number-change` (224–228) took that route because every number it drives has to be **pickable in a
  dropdown**: a slot moved onto, or a vacated slot handed to the next household, is offered from
  `1..quotaN`, so „a new band" and „inside the quota" are two rules and the second one wins. Sweep the
  numbers in use with `grep -rhno "\b2[0-9][0-9]\b" tests/e2e/*.spec.ts | cut -d: -f2 | sort -un`.
- **e2e spec files run in alphabetical path order, one worker, one shared database.** So a spec that
  *writes* shared state is only ever seen by the files sorting after it — `npx playwright test --list`
  prints the order, and a **rename moves a spec in that order** (batch 27's `portions.spec.ts` →
  `allowance.spec.ts` moved it from the middle to second). Anything a spec asserts as an **absolute
  count of a shared thing** is therefore a landmine: `settings.spec.ts` counted its version history
  as `3` and `4` and read the seeded version as `nth(2)`. It now takes a baseline with
  `versionCount(page)` and asserts `before + 1`, and reads the oldest version as `.last()` — the same
  claim, stated so that it does not depend on who ran first.
- **Two consecutive saves on the settings screen need a `page.reload()` between them in e2e.** A
  successful save *clears* the form, and the revalidated render that does it can land **after** the
  next `fill`, rewinding the field to the stored value; the second save then appends a version that
  changed nothing and every history index below it shifts. **`selectOption` loses the race too** —
  this bullet used to say it survived, and batch 29 watched WebKit fail the Ausgabetag spec on that
  claim twice in a row. Reload and re-assert the stored value before touching the field again,
  whichever control it is.
- **The customer record renders two different household blocks.** `/kunden/<active>` gives the live
  editor (`household-editor.tsx`), `/kunden/<archived>` gives `HouseholdReadOnly` in `[id]/page.tsx`.
  Both hold the same tiles, so a screen-level change has to be checked on one of each — **seed
  customer 6 is archived**.
- **Counts baked into prose go stale in files no story names, in both directions.** Removing two
  settings made "the ten fields of the settings form", "nine of the ten need no translation",
  "Seven of the nine settings", "printed only five of the eight settings" and a `toHaveLength(8)` all
  wrong at once; *adding* a field or a tile does the same. After any such change,
  `grep -rn "nine\|ten fields\|eight\|six tiles\|four figures" src/` — the suite catches only the
  assertion. The same applies to an **exported type you delete or rename**: `grep -rn "<TypeName>"`
  finds the `{@link}`-shaped references left behind in comments, which no gate sees.
- **Prettier does not reflow comments.** Shortening a sentence inside a `/** */` block leaves a
  ragged short line that `prettier --check` happily accepts — and so does an over-wide one, though
  the repo's width is 100. Re-wrap the paragraph by hand, and **measure with Python, not `awk`**: an
  em dash is three bytes, `awk` counts it as three columns, and every sentence carrying one is
  reported as a violation it is not.
  `git diff -U0 | python3 -c "import sys; [print(len(l[1:-1]), l) for l in sys.stdin if l.startswith('+') and not l.startswith('+++') and len(l[1:-1]) > 100]"`
- **A `toEqual` on a *whole* record is the assertion a new field breaks, and `tsc` cannot see it.**
  Adding a required field to a domain type (`IssuedCard.customerNumber`, batch 30) leaves every
  `expect(x).toEqual({ …every field… })` typechecking and failing at run time with a one-line diff.
  The compiler finds the *constructors*; only the suite finds the assertions. Same family as the
  „renaming a Prisma column is not finished when `tsc` is green" bullet — run the tests even when
  the wide break looks closed.
- **A required field added to a type a *writer* passes is a signal to split the type**, not to teach
  every writer the new field. `NewCard = Omit<IssuedCard, "customerNumber">` and `NewCustomer.card:
  NewCard` kept the slot the store's to fill in — which is the actual invariant — and cut the fixture
  break from ~50 errors to 17 as a side effect. `RegisteredCustomer extends NewCustomer` then
  re-declares `card: IssuedCard`, which TypeScript allows because the stored shape is assignable to
  the written one. Look for that split whenever a "wide break" is mostly test fixtures: it usually
  means the field belongs to the read model alone.
- **Prettier owns every markdown table in `docs/`, and `npm run lint` does not check it.** `lint` is
  `eslint` alone; markdown formatting is `npm run format:check` (the pre-commit hook runs it). Widen
  one cell and Prettier re-flows every row of that table, so run `npx prettier --write` on the files
  you touched *before* reading the diff — otherwise you are reviewing a re-alignment.

### Where batch 30 starts

Batch 29 (the customer balance) is **merged into `main`** — PR #126, squashed as `4658e1a`. So a
hand-out carries `paidCents` and no `paid` flag, the balance is `Σ(paidCents − priceCents)` derived
on every read, and the counter shows „Zu zahlen" beside „Saldo". Nothing in this batch touches money.

**This batch makes a customer number changeable.** It has been decided at registration and never
again since US-24, and four documents say so in as many words. A staff member may now move an active
or blocked household from the number it holds to any number that is free, from a section on the
customer record beside the group control — and **a new card is issued in the same act and the same
transaction**. Read `tasks/prd-us-30-change-customer-number.md` §Introduction before writing a line;
its worked 5 → 23 table is the specification.

Six hazards, all stated in `prd.json` and worth reading twice:

- **No card is ever re-labelled, and `read-card.ts`'s `numberOf` is the one line where it would
  happen.** It currently labels every card in the run with `customer.customerNumber`, so after a move
  the superseded cards would render as `23k4`, `23k3` … The cards left on the vacated slot are exactly
  what keeps that slot safe to hand out again: slot 5 has seen four cards, so the next household
  starts at `5k5`. Re-label them under 23 and slot 5 looks untouched, and the next household is
  printed a `5k1` that already exists out in the world.
- **`IssuedCard` gains a required `customerNumber`, which breaks every fake and every card fixture at
  once** — the same wide break `setPayment` and `highestIndexForNumber` levied. Story 2 owns it;
  `NewCard = Omit<IssuedCard, "customerNumber">` stays what a *writer* passes, because the adapter
  goes on reading the slot off the customer row inside the write's own transaction.
- **The move and the card are ONE transaction**, in one new port method
  `CustomerRepository.changeCustomerNumber(id, customerNumber, card)`. Split into two writes, a crash
  between them leaves a household on 23 carrying `5k4` and no query in the system can detect it. The
  precedent is `create`, which already writes a customer and their first card as one.

## 2026-08-31 - US-001 — Which numbers a household may be moved to (domain)

Implemented the pure rule US-30 rests on: which numbers a household already on the register may be
moved to, and whether a chosen one may still be written. Nothing above the domain calls it yet.

- `src/domain/customer/customerNumber.ts` — `choosableNumbers(currentNumber, takenNumbers, quotaN)`
  and `assertChoosableNumber(requested, currentNumber, takenNumbers, quotaN)`, beside `freeNumbers`
  and `assertFreeNumber` and built on them.
- `src/domain/customer/customerNumber.test.ts` — 12 named tests, written first and watched fail.
- `src/domain/errors.ts` — new `CustomerNumberUnchanged` carrying the number, and its code in the
  `DomainErrorCode` union (the 39th).
- `src/app/notice-tier.ts` — tiered `refusal`, and the header comment's count moved to „a 40th code“.

**Learnings for future iterations:**

- **`choosableNumbers` is a `Set` over `freeNumbers` plus `currentNumber`, sorted numerically — and
  the shape is the point.** An `includes(currentNumber) ? free : [...free, currentNumber]` would
  have been the obvious merge and it carries a branch that **cannot both-arm under the documented
  contract** (`takenNumbers` contains `currentNumber`, so `free` never has it), which the 100%
  branch gate would then demand a test for a case that cannot arise. The `Set` has no branch at all,
  and the numeric sort puts a current number above the quota last for free rather than by a rule of
  its own. Same family as the „unreachable `?? fallback`" bullet in the patterns block: **prefer the
  branchless construction over the one whose dead arm you then have to feed.**
- **Ordering refusals is how you avoid a special case.** `assertChoosableNumber` checks
  `requested === currentNumber` first and then delegates the other two verdicts to
  `assertFreeNumber` **unchanged** — because once unchanged is out of the way, any number still in
  play is somebody else's, so no „except my own number" filter is needed anywhere. Had the range
  check come first, a household parked above a lowered quota (US-14) that saved its own number would
  have been told its number is out of range, which reads as an instruction to move, and there is
  none.
- **The three-file `DomainErrorCode` change from the patterns block held exactly as written**, and
  the stale-count hazard in it is real: `notice-tier.ts`'s header said „a 39th code" with 38 in the
  union. Count with
  `python3 -c "import re,sys;print(len(re.findall(r'\"(\w+)\"',re.search(r'export type DomainErrorCode =(.*?);',open('src/domain/errors.ts').read(),re.S).group(1))))"`
  rather than by eye. „The eight red ones" in the same comment is untouched — this code is a refusal.
- **`notice-tier.test.ts` does not enumerate the codes and should not start**: the
  `Record<DomainErrorCode, NoticeTier>` is proved by the compiler, and its tests are about the
  *reading* of the table. A new refusal needs no test there.
- **No German string yet.** `CustomerNumberUnchanged` is not rendered anywhere until the control
  exists (story 6) — the sentence belongs to `kunden/[id]/actions.ts` and `de.ts` with the screen
  that raises it, exactly as `GroupUnchanged`'s does.

## 2026-09-01 - US-007 — E2E: a household moves, and both slots stay honest

One new spec, `tests/e2e/number-change.spec.ts`, eight tests, green on **both** engines
(`npm run test:e2e` and `npm run test:e2e:webkit`, 196 passed / 1 skipped each). No production code
changed — the story is the proof, not a fix.

The walk: a household holding `224k4` moves onto slot 225, which an archived household left five
cards deep, and is printed `225k6`. Then the card view (every superseded card under **its own**
number, „Karten insgesamt" = 5), the intake's pool, the counter on four different queries, the
cards-due list either side of a second move, a fresh registration onto the vacated 224 printed
`224k5`, and the lost race.

- `tests/e2e/number-change.spec.ts` (new). Band **224–228**; reuses `releaseNumbers`,
  `fillPersonalData`, `hydrated` and the `dueRow`/`badgeCount` shapes from `age-13.spec.ts`.

**Learnings for future iterations:**

- **The batch note's „take a new band, start at 351" does not survive this story's own constraint.**
  Both the slot moved *onto* and the slot *vacated* have to be pickable in a dropdown — the record's
  control offers `1..quotaN` and `/kunden/neu` offers the free ones — so every number here is inside
  the quota of 240. The band is **224–228**, which was free of every other spec (below 240 the taken
  ones are 201–207, 211, 221–223, 231–236, 239) and below 315, so `group-walk.spec.ts`'s highest
  walkable RED number is untouched and the households could be seeded RED. Being RED is what let the
  spec reuse the RED distribution Thursday `2026-01-08` that `reissue.spec.ts` and
  `card-number.spec.ts` already pin — a BLUE band would have needed a different day for one
  assertion. **Read the band bullet as two rules, not one: „a new band" and „inside the quota if a
  dropdown has to offer it", and the second one wins.** The consolidated numbers-in-use sweep is one
  command: `grep -rhno "\b2[0-9][0-9]\b" tests/e2e/*.spec.ts | cut -d: -f2 | sort -un`.
- **Two ACs describe a screen and an arithmetic that do not exist, and both were written as what is
  true.** „The free-slot count on the waiting list is one higher immediately after the move" fails
  twice over: `/warteliste` has no free-slot count at all (a banner naming *one* free number and an
  applicant, plus a boolean „Platz frei" badge on `/kunden`), and **a move can never change the
  count** — it swaps one taken number for another, so `|taken|` is invariant. US-006's browser check
  had already noticed the second half („Noch 225 freie Nummern" before and after). The honest
  version is asserted on `/kunden/neu`, where the count actually lives: the vacated number is on
  offer, the taken one is not, and the figure is unchanged — with the comment saying that „it went
  up" is the first thing a reader expects here and would be wrong. Third AC in this batch to be
  contradicted by the register itself, after US-003's index rule and US-004's `k1`.
- **A card number resolves through the *slot*, so „the old card number resolves to whoever holds
  that slot today" has two answers and both are worth asserting.** `findByCustomerNumber` prefers
  the active holder and falls back to the most recent archived one, so `224k4` is `NOT_FOUND` while
  nobody holds 224 and becomes the *successor's* superseded card the moment somebody is registered
  on it — `OUTDATED_CARD`, naming `224k5`. Neither answer is ever the household who carried it. The
  same lookup is why the mover can move **onto** 225 while the archived household still sits on that
  number: the partial unique index is `WHERE status <> 'ARCHIVED'`.
- **A move is the one write that can only ever *shorten* „Karten neu ausstellen".** It issues a card
  with today's counts and today's group, so a household on the list for stale counts leaves it and
  no move can put one on. Asserted with `badgeCount` either side of two moves — unchanged across the
  first, one lower across the second — which is the self-comparing shape `age-13.spec.ts` uses for a
  figure that counts the whole shared register.
- **`selectOption` needs `hydrated()` before it, on both selects this spec drives.** The record's
  number control and the intake's number dropdown are both controlled, and the patterns block's
  „`selectOption` loses the race too" bullet is about exactly this window. `pickNumber` wraps
  `hydrated` + `toPass`, which is `fillSticky`'s shape for a `<select>`; `card-number.spec.ts` does
  a bare `selectOption` right after `goto` and has been lucky.
- **The lost race is driven with a second real tab**, `page.context().newPage()` and the same
  `register` helper, rather than a Prisma insert: „the number is taken by another registration" is
  the AC, and a hand-written row would not exercise the intake's own allocation. The refusal comes
  back as `de.customers.errors.customerNumberUnavailable` — the intake's sentence, shared — and
  `freshChoicesAfterRace` is what makes the follow-up assertions possible: the number is gone from
  the options and the control has fallen back to the household's own number in the same render.
- **The seeded card reason word is `LOST`, not `LOSS`** — `cardReasons.LOST` / `"LOST"` in the
  `Card.reason` column. `tsc` catches the dictionary half; the Prisma half is a validated string and
  would have failed at run time.
- **`de.customers.cardView.supersededEntry` over `toHaveText([…])` is the assertion that proves the
  whole story in one line**: four entries, in order, each naming `224kN` with its own issue date and
  reason. A `toContainText` would have passed on a re-labelled list.

**Learnings for future iterations:**

- **The AC's „final grep“ is the story, not its closing check — and it finds files the PRD did not
  list.** Four documents were named; the sweep turned up two more that stated the rule as fact:
  `Customer.customerNumber`'s *own* schema comment („The slot this household holds“ — silent on
  whether it may move) and `updateDetailsAction`'s header in `src/app/`, which repeated ports.ts's
  sentence almost word for word. The pattern is worth keeping: **a claim that is worth writing once
  gets copied**, so grep the *phrasing* (`"fixed at registration"`, `"released only by archiving"`,
  `"never edited"`, `"nicht ändern"`) rather than the concept, across `src/ prisma/ docs/ tasks/`.
  What it must *not* flag: `scripts/ralph/prds/*.json` (the batch inputs are a historical record of
  what was asked, like the PRDs) and the identical wording used about settings versions and
  certificates, which really are never edited.
- **Correcting a claim is not deleting it.** Every rewrite here kept the *argument* and changed only
  what stopped being true — ADR-007's row still says why the column is stored, ADR-008 still says a
  number is a slot, US-24's Non-Goal still says a number change is not a record correction (which is
  precisely why US-30 gave it its own section rather than a field in the details form). A rewrite
  that drops the reasoning leaves the next reader with a rule and no way to tell whether it still
  applies.
- **A superseded ADR row is amended in place, with the amendment stated out loud.** ADR-007 is not
  superseded by ADR-016 — one of its four exceptions changed shape. The note under the table names
  which row and says „amended, not superseded“, because a reader who finds ADR-016 first needs to
  know ADR-007 still stands, and a reader who finds ADR-007 first needs to know one row moved.
- **`arc42.py new-adr` writes the row as `Pending` and does not touch the intro count.** Four manual
  steps after it, every time: Accepted in the file, Accepted in the row, the counting word in the
  intro sentence, and `npx prettier --write` on chapter 9 (the appended row is narrower than the
  table and Prettier re-flows all of it). This iteration added a fifth: the **row Prettier writes is
  wider than the table**, so the intro paragraph one line above it went to 105 characters when
  „fifteen“ became „sixteen“ — Prettier does not reflow prose, so re-wrap it by hand.
- **`prettier --check` cannot parse `prisma/schema.prisma`** (no parser inferred) — it is excluded
  from `npm run format:check`, so a schema comment is hand-wrapped and nothing checks the width.
  Measure it the same way as a `/** */` block, with Python and not `awk`.
- **A code span must not be wrapped across two lines in Markdown.** Prettier reacts by *removing the
  indentation* of the continuation line, which silently breaks the list item it sits in — it showed
  up here as `card.index)` landing in column 0 inside a nested bullet in root `CLAUDE.md`. Keep the
  span on one line and rewrap the sentence around it.
- **Chapter 9's „Ordered by date“ smaller-decisions table had drifted**: batch 30's own
  2026-08-31 row had been appended after 2026-08-07 rather than sorted in. Moved. A table that
  states its own ordering rule is worth re-checking whenever a batch appends to it.
- **The counts in chapter 5 are approximations that a batch inherits.** „35 use cases“ was already
  one below the 36 exported use-case functions at `main` (`describeAllowances` and
  `countCardsDueForReissue` sit beside their siblings in one file each), so the honest move is to
  carry the **delta** — +2 for this batch — rather than to recount and silently restate someone
  else's number. „five separate forms saving through five use cases“ on `/kunden/[id]` was stale in
  the other direction: there are seven form actions in `[id]/actions.ts`, now stated as such.

  operations for DF — start/stop, backup, eggs, balance, correcting a hand-out — and has no
  per-screen administrative how-tos, so a number change has nowhere to go in it without inventing a
