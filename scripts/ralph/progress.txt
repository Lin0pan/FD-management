## Codebase Patterns
- **Adding a `DomainErrorCode` is a three-file change**: the union in `src/domain/errors.ts`, the
  class beside it, and `TIERS` in `src/app/notice-tier.ts`. `TIERS` is a `Record` over the union, so
  the *build* fails until the code is tiered — that is the mechanism, not an obstacle. The header
  comment of `notice-tier.ts` counts the codes ("a 32nd code…", "the six red ones"), so it goes
  stale silently; update it with the entry.
- **The same mechanism guards `SettingsChange`**: its `switch` in `src/app/einstellungen/page.tsx`
  is exhaustive with no `default`, so adding a member to the union fails the build until the screen
  renders it. Do not silence it with a `default` branch.
- **An error class with no caller yet still needs a test**, because `domain/` coverage is gated at
  100%. `src/domain/errors.test.ts` is where those live — see the `MissingAuditReason` block for the
  shape, including the comment saying which story will call it.
- **`errors.ts` cannot import from `domain/card/`**: `cardNumber.ts` imports `errors.ts`, so a
  message that wants to read `66k1` writes the `k` inline rather than calling `formatCardNumber`.
- **Adding a field to `Settings` is a wide change before it is a deep one.** `createSettings` is
  called from the repository, the seed, the settings server action and every hand-written fake in
  the application tests; all of them must supply the new field before anything compiles. Land the
  field with a placeholder value at each call site, then replace them in the story that owns each.
  Get the *files* out of a wide break rather than the errors:
  `npm run typecheck 2>&1 | grep -E "^src/" | cut -d'(' -f1 | sort -u`.
- **A test that merely *uses* a field is not a test *of* it.** Several `settings.test.ts` cases
  reach for an arbitrary second field to prove the same-instant tie rule or the audit's changed-field
  list. When that field goes away, **re-point them**, do not delete them — deleting takes an
  unrelated rule with it and drops coverage below the gate.
- **A Prisma `P2002` cannot always name *which* constraint was broken.** `meta` is
  `{ modelName, target: [columns] }`, but where two unique indexes both cover the offending row
  SQLite reports only one of them, and not the one that was declared or created first. Where the
  distinction matters, match the target for the *shape* and then ask the database the question that
  actually distinguishes the two faults (`card-repository.ts`'s `issue` counts the customer's own
  rows on that index). For a **nested** write Prisma reports the *rooted* model — a card refused
  inside `customer.create` comes back as `modelName: "Customer"` — so the model name alone tells
  nothing about which table failed.
- **Regenerating `prisma/migrations/` drops the hand-written partial unique index** on
  `Customer.customerNumber` (`Customer_customerNumber_onRegister_key`) at the end of the migration
  SQL. `src/infrastructure/prisma/schema.test.ts` greps for it and for the `onDelete: Restrict`
  clauses, so a lost line fails CI rather than production — but re-add it deliberately. Three things
  batches 25–27 each had to learn:
  - **Delete `data/fd.db` before `migrate dev`**: with the old migration row still in
    `_prisma_migrations`, Prisma refuses to regenerate and writes nothing.
  - **Verify with `diff`, not by reading the new file**:
    `git show HEAD:prisma/migrations/<old>/migration.sql > /tmp/old.sql && diff /tmp/old.sql <new>`
    states in a few lines what the story is allowed to have changed. Anything else is a Prisma
    version drifting the DDL under you, which no gate would attribute to this commit.
  - **`migrate dev` applies the migration *before* the hand-written index is appended**, so the
    database it leaves does not have the index even though the committed SQL does. `npm run db:reset`
    afterwards is what makes the two agree — check with
    `SELECT sql FROM sqlite_master WHERE name='Customer_customerNumber_onRegister_key'` rather than
    trusting that the reset ran.
  - A regeneration **renames a directory that documents cite by name**. `grep -rn "<old-timestamp>_init"
    docs/ src/ tests/` afterwards; prefer the `prisma/migrations/*_init/migration.sql` glob, which
    survives the next one.
- **Never `pkill -f "next dev"`, and never `pkill -f "node.*next-server"`** — both patterns match the
  Bash tool's own wrapper command line and kill the shell (exit 144, no output). **And `ss` is not
  installed in this sandbox**, so `ss -ltnp | grep :3000 || echo free` reports "free" for every port,
  always: the `||` fires on `command not found`. (Batch 27's per-story notes recommend `ss` in two
  places — they are wrong; that is the bug this bullet exists to stop.) Check
  `ps aux | grep "[n]ext-server"` — the bracket keeps the pattern out of its own match — and
  `kill <pid>` by number.
- **A stale `next start` from an earlier iteration silently serves a mixed build.** The new
  `npm run start` fails with `EADDRINUSE` in the background while the page still renders, from the
  old server reading the *new* chunks off disk — a couple of console 500s are the only symptom.
  Check for a live server (`ps`, above) **before** trusting any browser check.
- **`npm run db:reset` does not reach a server that is already running.** It deletes `data/fd.db`,
  and SQLite keeps serving the running process from the deleted inode, so the screen goes on showing
  the pre-reset data. Restart the server after a reset, or the verification is of the old database.
  `db:seed` fills settings only — customers are not seeded, so a reset empties whatever manual
  clicking built up (the e2e suite makes its own registers).
- **Changing a seeded policy value moves e2e expectations.** `grep -rn ',00 €' tests/e2e/` before
  editing a number in `seed.ts`.
- **The e2e customer-number bands, as they now stand.** Below the quota of 240: counter 201–206 and
  239, allowance 211, serve 221–222, reminders 231, registration 232–234, card numbers 236. Above it:
  block 241, reissue 251, age-13 271, customer-list 281–285, customer-record 291–293, group-progress
  301–303, group-walk 311–315, price cap 321, eggs 331–334. A spec whose number must be **pickable in the
  /kunden/neu dropdown** has to sit below 240 — the pool is `1..quotaN` — and everything else should
  stay above it, clear of the low sequence the allocating specs (registration, card, archive,
  reregistration) consume. **A new spec takes a new band**; do not borrow another spec's numbers.
- **e2e spec files run in alphabetical path order, one worker, one shared database.** So a spec that
  *writes* shared state is only ever seen by the files sorting after it — `npx playwright test --list`
  prints the order, and a **rename moves a spec in that order** (batch 27's `portions.spec.ts` →
  `allowance.spec.ts` moved it from the middle to second). Anything a spec asserts as an **absolute
  count of a shared thing** is therefore a landmine: `settings.spec.ts` counted its version history
  as `3` and `4` and read the seeded version as `nth(2)`. It now takes a baseline with
  `versionCount(page)` and asserts `before + 1`, and reads the oldest version as `.last()` — the same
  claim, stated so that it does not depend on who ran first.
- **Two consecutive saves on the settings screen need a `page.reload()` between them in e2e.** A
  successful save *clears* the form, and the revalidated render that does it can land **after** the
  next `fill`, rewinding the field to the stored value; the second save then appends a version that
  changed nothing and every history index below it shifts. `selectOption` happens to survive the
  race, `fill` does not — reload and re-assert the stored value before typing again.
- **The customer record renders two different household blocks.** `/kunden/<active>` gives the live
  editor (`household-editor.tsx`), `/kunden/<archived>` gives `HouseholdReadOnly` in `[id]/page.tsx`.
  Both hold the same tiles, so a screen-level change has to be checked on one of each — **seed
  customer 6 is archived**.
- **Counts baked into prose go stale in files no story names, in both directions.** Removing two
  settings made "the ten fields of the settings form", "nine of the ten need no translation",
  "Seven of the nine settings", "printed only five of the eight settings" and a `toHaveLength(8)` all
  wrong at once; *adding* a field or a tile does the same. After any such change,
  `grep -rn "nine\|ten fields\|eight\|six tiles\|four figures" src/` — the suite catches only the
  assertion. The same applies to an **exported type you delete or rename**: `grep -rn "<TypeName>"`
  finds the `{@link}`-shaped references left behind in comments, which no gate sees.
- **Prettier does not reflow comments.** Shortening a sentence inside a `/** */` block leaves a
  ragged short line that `prettier --check` happily accepts. Re-wrap the paragraph by hand.
- **Prettier owns every markdown table in `docs/`, and `npm run lint` does not check it.** `lint` is
  `eslint` alone; markdown formatting is `npm run format:check` (the pre-commit hook runs it). Widen
  one cell and Prettier re-flows every row of that table, so run `npx prettier --write` on the files
  you touched *before* reading the diff — otherwise you are reviewing a re-alignment.
- **Recording an ADR is four steps, and the script does one of them.**
  `python3 .claude/skills/arc42/scripts/arc42.py new-adr "<decision as a sentence>"` picks the
  number, renders the template and appends the chapter 9 index row as `Pending`. By hand afterwards:
  set `Accepted` in the file **and** the row, **re-count** the intro sentence („The thirteen
  decisions …“), and `npx prettier --write` chapter 9 — the appended row is narrower than the table
  and Prettier re-flows every row of it. Finish with `arc42.py check`, which sees structure and dead
  links but never staleness.
- **Two files carry the story range and neither is anybody's story:**
  `docs/architecture/01-introduction-and-goals.md` („one PRD per user story, US-01 to US-nn“) and
  the `tasks/` row of `docs/architecture/README.md` say the same thing, and both go stale on every
  batch that adds a PRD. `grep -rn "US-01 to US" docs/`.
- **Documentation has no gate.** Nothing fails CI when a chapter goes stale, so a change that adds or
  removes a concept finishes with an explicit sweep — `grep -rin <concept> --include="*.md" .` — and
  the answer is not always zero: `docs/architecture/01`'s non-goals and `09`'s „Decisions that were
  reversed“ exist precisely to keep a withdrawn idea named, with its reason. **`docs/architecture/`
  is the tree to update**; `docs/technical_documentation.md`, `tech_stack_architecture_sketch.md` and
  `fd_dev_setup_overview.md` were retired in #102 and only the archived progress logs still name them.
- **`docs/archiv/` is annotated, never rewritten** (root `CLAUDE.md`). A dated `> **Note (YYYY-MM-DD).**`
  blockquote goes after the *block* carrying the claim, not inside the table cell or list item that
  states it, and names which bullets it answers when it follows several. The per-story PRDs in
  `tasks/` are the same kind of record: they say what was asked for, so a superseded one gets a
  banner and the rest are left alone.
- **`playwright-cli` needs a role locator, not a testid, to fill the counter's Nummer input**, and a
  `cmd-a || cmd-b` shell chain hides a silent no-op — the first command exits 0 without filling
  anything. Run the fill on its own and re-snapshot to confirm it landed. Verify against
  `npm run start` (production build), not `next dev`.
- **WebKit's nav-bar click is flaky at roughly one failure in two full-suite runs**
  (`navigation.spec.ts` „von Kunden verwalten aus …“, `waitForURL` timing out after the click). It

- **Prior runs' patterns are in the archive**, not in this file:
  `scripts/ralph/archive/2026-08-25-us-28-egg-allowance/progress.txt` is the most recent (the first

Five hazards, all stated in `prd.json` and worth reading twice:

- **The sum is against the PRICE, not the amount asked for.** `balance = Σ(paidCents − priceCents)`.
  Against the amount to pay the definition never settles: a household paying the full 8,00 € they
  were asked for gives `8,00 − 8,00 = 0` and their 3,00 € debt is charged again next week, and a
  credit never shrinks. This was an ambiguity in DF's own requirement, corrected and confirmed on
  2026-08-28. The `askedCents` the colour mark compares against is a *different* quantity, derived by
  replaying the history. **Do not "simplify" the two into one.**
- **Story 3 leaves a deliberate bridge.** Between story 3 and story 4 the use cases translate the old
  boolean into an amount (`paid ? priceCents : 0`) — exactly today's behaviour, so the tree stays
  green. Story 4 removes it. Do not leave the tree in that state.
- **Fifth regeneration of `prisma/migrations/`.** Same drill as 25–28: delete `data/fd.db` first,
  re-add the hand-written partial unique index, verify with `diff` against `git show HEAD:…`, and
  `npm run db:reset` afterwards. The patterns bullet above has all four traps.
- **`setPaid` becomes `setPayment` on the port**, so every hand-written fake
  `DistributionRecordRepository` must gain it in the same commit — including the one in
  `read-group-roster.test.ts`, which implements the port in full and has nothing to do with payments.
