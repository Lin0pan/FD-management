## Codebase Patterns
(Carried forward by hand from the US-11 log — the archive rotation wipes this file, so the patterns
block has to be pasted into the fresh one. The other durable channel is the CLAUDE.md files.)
- Adding a method to a port interface (e.g. CustomerRepository) forces EVERY implementer to compile:
  the real Prisma adapter AND the hand-written fakes, which live in several test files —
  customers.test.ts, certificate-reminder.test.ts, lookup-customer.test.ts,
  cards-due-for-reissue.test.ts and distribution/record-attendance.test.ts.
  `grep -rln "implements <Port>" src/` before you start. Miss one and typecheck fails, not lint.
- Adding a field to RegisteredCustomer ripples the same way: every fake `create` returning
  `{ ...customer, id }` and every builder literal needs the new field.
- Adding a REQUIRED column to Customer ripples further still: ~12 fixtures write customer rows
  straight through Prisma (5 infra *-repository.test.ts + 7 tests/e2e/*.spec.ts). That is the price
  of a column the database will not default — and it is the point, because a fixture that skipped it
  would be a row the feature can never find. `grep -rn "prisma.customer.create" src tests`.
- `issueCard` (application/customers/issue-card.ts) is the ONE path by which a card comes into
  existence; `reissueCard` delegates to it and only narrows the reason. Never write a second issuing
  path — validity is "holds the highest index", so a parallel path is how two valid cards appear.
- Prisma migrations are pre-release disposable. `npx prisma migrate dev --name init` REGENERATES the
  single init migration and DROPS the hand-written partial unique index at its end — re-append it
  from the previous migration (`git show HEAD:prisma/migrations/<old>/migration.sql | tail -16`) or
  the slot rule is enforced by application code alone. `npm run db:reset` afterwards, and note that
  `migrate dev` refuses non-interactively if the dev db is ahead — delete data/fd.db first.
- Status changes go through `transition(from, to, reason?)` in domain/customer/status.ts, never an
  ad-hoc status assignment; persist via CustomerRepository.setStatus — except the archive, which has
  its own `archive(id, reason, archivedAt)` write because it stamps three columns and clears
  blockReason in one statement.
- Derive-don't-store: household counts, ages, card validity and the card number are all derived on
  read (readCustomer / readCard / describeAllowance), never stored. The only two exceptions are
  named in the root CLAUDE.md — the card's printed counts, and the folded name search keys.
- Narrowing a nullable pair that is non-null "exactly when status is X" belongs in the ADAPTER, not
  in the use case: define the narrowed type in ports.ts (e.g. `ArchivedCustomer extends
  RegisteredCustomer`) and let infrastructure refuse a hand-edited row with InvalidCustomerRecord.
  Doing it in application/ costs a defensive branch against the 100% coverage gate.
- Prisma defaults `onDelete` to `SetNull` for an OPTIONAL relation and `Restrict` for a required one,
  so every nullable relation must spell `onDelete: Restrict` out. schema.test.ts greps the schema for
  the words AND the migration SQL for `ON DELETE SET NULL` / `ON DELETE CASCADE`.
- A self-referencing FK (Customer.previousCustomerId) means "children first" is not enough to tear the
  register down: `clearRegister` nulls the links before `customer.deleteMany()`.
- SQLite reports a FK violation as P2003 with EMPTY `meta` — unlike P2002, the offending column cannot
  be read off the error, so attribution has to come from what the write itself contains.
- German UI strings only in `src/i18n/de.ts`; inflected forms are functions in the dictionary.
- The Edit tool struggles with strings containing umlauts/em-dashes; patch such lines with a small
  `python3 - <<'PY'` heredoc instead of fighting it.
- HTML forms do not nest: a panel with its own submit button on a screen that is already a form has
  to be a SIBLING, with the state they share lifted into a parent client component.
- A `key` change is the cheapest way to reset a form that mixes controlled and uncontrolled fields —
  remounting resets both kinds, and `useActionState`'s message with them.
- Convert a `Date` to `YYYY-MM-DD` on the SERVER before it reaches an `<input type="date">`; read in
  the browser's zone a midnight-UTC day lands on the day before. `germanDate` is for display only.
- A `key` remount is invisible to Playwright: after clicking something that applies a pre-fill, WAIT
  for the new form (a banner, a pre-filled value) before typing. A `fill` on the node about to be
  replaced is thrown away with it, and the submit then fails on a field the spec believes it filled.
- An e2e spec that has to prove "not this row" is strongest when the excluded row is *hard* to
  exclude: give the archived household and the active one the same surname, so only the status
  filter keeps them apart.
- Killing the e2e server: the process is called **`next-server`**, not `next start`, so
  `pkill -f "next[ ]start"` finds NOTHING and leaves it running. Use `pkill -f "next-server"` (and
  check with `ps aux | grep "[n]ext-server"` — it exits 1/144 when it killed something). A survivor
  is adopted by `reuseExistingServer`, which serves the OLD build and skips the delete-migrate-seed
  chain, so the whole suite fails at once: `PrismaClientKnownRequestError: The table main.Customer
  does not exist` or duplicate rows in `beforeAll`. Whole-suite failure = stale server, not your spec.
  (The `[ ]` trick is still needed for whatever pattern you do use, or pkill matches its own shell.)
- A new e2e spec has to claim a customer number nobody else holds: the shared `data/e2e.db` is
  seeded once per run and every spec inserts into it. Taken so far: counter 201-206/239, portions
  211, serve 221-222, reminders 231, block 241, reissue 251, age-13 271, customer-list 281-285,
  record 291 - and the registration/card/archive/re-registration specs allocate the LOW sequence
  through the form. A collision surfaces as `Unique constraint failed on the fields:
  (customerNumber)` inside `beforeAll`, i.e. one spec failing while the other 70 pass; a whole-suite
  failure is the stale-server trap instead. `grep -rn "CUSTOMER_NUMBER = \|NUMBERS = " tests/e2e`.
- The cards-due list answers with ONE reason and the counts answer first (`staleCardReason`), so a
  spec that wants to see `GROUP_CHANGE` must first bring the card's printed counts up to date - a
  reissue between the two edits. The same ordering applies to the counter: a lapsed certificate
  changes the verdict, so record the renewal before asserting anything about a group or a card.
- A figure that aggregates the WHOLE register - the two group sizes, the cards-due badge - is only
  ever compared with itself in an e2e spec: read it before the edit, assert it as a delta after.
  Neighbouring specs register households of their own.
- A pure rule that has to hand the CALLER's row back is generic over it — `recordForDay<T extends
  AttendanceRecord>`, `nextInLine<T extends WaitingApplicant>`. Declare the minimal interface the
  rule reads, constrain `T` to it, return `T`: the application layer keeps its richer entry and the
  domain never grows a field it does not use.
- A "nothing to report" outcome is a variant of the result union (`WAITING_LIST_EMPTY`,
  `NOT_FOUND`), never `null`/`undefined` — the UI switch stays exhaustive and a caller cannot
  mistake "no one" for "not asked".
- Every expiry question in the system goes through `isExpired(certificate, today)` in
  domain/customer/certificate.ts. Do not re-compare `validUntil` inline anywhere — the "valid
  through its last day" boundary would drift.
- A use case that must do TWO things in an order (register, then remove from the list) is a use case,
  not a server action calling two of them: app/ is thin by rule, and "remember to do B after A" is
  exactly what a screen forgets. Delegate to the existing use case (`registerCustomer`) rather than
  re-implementing it, like `reissueCard` → `issueCard`.
- Validation of a typed-in record belongs in a domain factory (`createCustomerDetails`,
  `createWaitingListDetails`), not in the use case: the use case then reads as clock → factory →
  write, and the 100% gate is paid once in a domain test rather than per use case.
- A new port method costs every implementer a compile, so a WHOLE new port (WaitingListRepository) is
  cheaper than widening CustomerRepository — and the fakes stay small. Check `grep -rln "implements
  <Port>" src/` before widening an existing one.
- The audit `why` is a human sentence except where no human judged: those carry a machine key=value
  (`reminderCount=2`, `customerNumber=7`). Never put a German sentence in application code — the
  dictionary is `src/i18n/de.ts` and the layer below it has no access to it.
- Use the caller's own instant instead of a second `clock.now()` when two writes belong to one event
  (`customer.registeredOn` stamps the waiting-list removal that registration caused).
- Prettier reorders nothing but reflows long import lists and tables; run
  `npx prettier --write <files>` after hand-editing docs/technical_documentation.md tables, or the
  lint-staged hook rewrites them under you.
- An adapter for a table with NO relations is exempt from `clearRegister`: a spec that owns such a
  table clears it with its own `deleteMany()` in `beforeEach`. Only the register needs children-first.
- Regenerating the init migration also leaves the DEV database without the re-appended partial unique
  index — `migrate dev` applied the file before the index was pasted back on. Always finish the
  sequence with `npm run db:reset`, which re-runs the completed migration.
- A nullable column whose domain counterpart is a non-nullable `""` (contactNote) is translated in
  the ADAPTER, both ways, in one `toEntry`/`create` pair. The layers above never see the null, and the
  column keeps a single representation of "not answered".
- A "remove" that must be idempotent scopes its `where` to the rows still eligible
  (`{ id, removedOn: null }`) and uses `updateMany`: a second call updates nothing instead of
  overwriting the first reason, and an unknown id is not an error the adapter has to invent.
- A `"use server"` module may export **nothing but async functions**, so a Zod schema, a helper or a
  state interface has to live beside it — `registration-input.ts`, `*-state.ts`. That is also how a
  second screen reuses a form's parsing: put the schema in the plain module and both actions import
  it, rather than copying it and letting the two drift.
- Reusing a whole form on a second screen is a `submit` prop plus a hidden field, not a second copy
  of the form. `RegistrationForm` takes `submit` (default `submitRegistration`) and `entryId`; the
  prefill type carries the extra fields as OPTIONAL, and which screen fills them is documented on the
  type, because the difference is a decision rather than an omission.
- `setState` inside `useEffect` is an ESLint ERROR (`react-hooks/set-state-in-effect`). To reset a
  form after a successful action, put a **counter in the action's state** and use it as the `key` —
  derived, no effect. A counter beats keying on the saved values: two applicants with the same name
  produce an identical state, and a form that resets on a value that did not change keeps the
  previous entry's address.
- A page that needs "is a slot free" asks `proposeRegistration` and reads `customerNumber !== null`.
  It throws `NoSettingsInForce` on an unseeded database — catch that one code and render without the
  banner rather than taking the screen down (`/kunden/neu` does the same for its form).
- Playwright's `webServer` has `reuseExistingServer: !CI`, and `npm run start` serves the BUILT app.
  After changing a string or a component, `npm run build` and `pkill -f "next[ ]start"` before
  re-running specs, or the assertions run against the previous build.
- To put an expired certificate at the head of a list in an e2e spec, add the applicant with a valid
  one and then move the app's today past it by writing `data/e2e-now.txt` (the `FD_FIXED_NOW_FILE`
  seam). Delete the file in a `finally` — it freezes today for every spec that follows.
- `getByRole("heading", { name: X })` is a substring match: a section heading containing the page
  heading ("Auf die Warteliste setzen" vs "Warteliste") is a strict-mode violation. Pass `exact:
  true` for the `h1`.
- The e2e suite has TWO Playwright projects: `chromium` on port 3000 over the shared `data/e2e.db`,
  and `isolated` on port 3001 over its own empty `data/e2e-isolated.db` (`ISOLATED_SPECS` in
  playwright.config.ts). A spec belongs in `isolated` only when it must OWN the register — set the
  quota, or fill every slot. On the shared database that is unreachable: other specs seed customers
  on numbers 201–271, so the quota (which may not fall below the active count) always leaves a dozen
  low numbers free. Everything that merely writes stays on the shared server.
- Each server has its OWN `FD_FIXED_NOW_FILE`, so pinning the clock in one project cannot move the
  other's calendar. A new server needs its now-file added to `.gitignore` beside `data/e2e-now.txt`.
- A `node -e "…"` command inside playwright.config.ts is double-quoted by the shell, so any array
  literal in it must use SINGLE quotes — `JSON.stringify` emits double quotes and the shell eats
  them (`ReferenceError: data is not defined`).

- Two functions that state the SAME rule in two shapes (a per-row comparison and a SQL range) must
  be built from ONE private window/helper, or they drift on the boundary day. `certificateState` and
  `validUntilRangeFor` both read `certificateWindow`; `isExpired` stays the single expiry comparison.
- A strict parser the counter needs (`parseCounterQuery` throws) gets an `…OrNull` sibling for the
  screen where "not a number" is an ordinary answer; the throwing one delegates to it, so the rules
  cannot relax on one path.
- A `Record<Union, T>` lookup beats a switch or an if-chain when every case is a value: exhaustive by
  type and it adds NO branches for the 100% coverage gate to demand tests for.
- Default parameters and `?? fallback` inside application code each create a branch the gate wants
  covered. Prefer a REQUIRED parameter where the caller always has the value (`describeAllowances`
  takes a required `date`; `describeAllowance` keeps the optional one).
- A per-row use case that needs settings must not call `describeAllowance` in a loop — that is one
  `listVersions()` per row. Use `describeAllowances(deps, households, date)`, which reads the history
  once and shares the private arithmetic. A test asserting `settings.reads === 1` pins it.
- Prisma cannot express "the LATEST related row satisfies X" — `certificates: { some: … }` matches a
  notice the household has long since renewed. Use `$queryRaw` with a correlated subquery for the ids
  and feed them back as `id: { in: … }`. Build the bounds with `Prisma.sql` fragments joined by
  `Prisma.join`, and never alias a table `inner` (a SQLite keyword) — `latest` works.
- `$queryRaw` binds a JS `Date` correctly against Prisma's SQLite DateTime columns; verified against a
  throwaway migrated database.
- Faker's default (English) name lists contain German-looking surnames — `Mueller` is in there. A
  fixture that seeds dozens of faker households and then asserts an EXACT result set for a name search
  is a flake: one of the other draws will eventually fold onto the prefix. Give the searched household
  an INVENTED name (`Müllerhoff`) and search a prefix long enough to reach the invented part. The test
  passed alone and failed in the full file, which is what this looks like when it bites.
- Prisma's SQLite provider quotes identifiers with BACKTICKS — ``SELECT … FROM `main`.`Customer` WHERE
  `main`.`Customer`.`group` = ?``. A test that reads the generated SQL off a `log: [{ emit: "event" }]`
  client must match backticks, not double quotes, and must scope the assertion to the text after
  `WHERE` — every column name also appears in the select list.
- Filter state that must be bookmarkable belongs in a plain **GET form**, not in a client component:
  submitting navigates, which writes the filters into the URL for free and keeps the screen a pure
  server component. Parse the parameters with a Zod object whose every field carries
  `.catch(undefined)` — a hand-typed `status=foo` is then a filter nobody set rather than a crash,
  and `searchParams` arriving as `string[]` is handled by the same fallback.
- A German query parameter per filter (`suche`, `status`, `gruppe`, `nachweis`, `archiv`), matching
  `datum` / `nummer` on /ausgabe. A checkbox is `value="1"` and absent when unticked, so the default
  view is the bare URL.
- A fixture that stacks a certificate RENEWAL must record it after the one `repository.create` wrote:
  `create` stamps `recordedAt` from `card.issuedAt` (= the fixture's TODAY), and "the certificate on
  file" is the latest `recordedAt`. A renewal dated earlier is silently not the current one.
- A seeded `Card.reason` must be a real `CardIssueReason` — `FIRST_ISSUE | LOST | STALE_COUNTS |
  OTHER`. An invented one ("REPLACEMENT") passes Prisma (the column is a string) and then throws in
  `parseCardIssueReason` on EVERY page that reads cards, including `/` (the cards-due badge). A fixture
  that breaks unrelated specs is usually a string the domain parses, not a relation.
- An aggregate the whole shared register feeds (the group balance, the cards-due badge) is asserted as
  a DELTA: read it off the screen in `beforeAll` BEFORE seeding, then assert baseline + what this spec
  inserted. An absolute figure is an assertion about whichever specs ran first.
- Regenerating the init migration RENAMES its directory (`git status` shows a rename). `schema.test.ts`
  reads the migrations directory rather than a fixed path, so it survives — anything that pins the
  folder name would not.

- A snapshot column on a card is the ONLY honest way to answer "has X changed since the card was
  printed". `Card.groupAtIssue` joins `grownUpsAtIssue`/`childrenAtIssue` under the same argument;
  the alternative — inferring a move from `issuedAt` — has nothing to compare against. Adding one is
  a ~40-file ripple (schema, migration regen, every `IssuedCard` literal in 9 application tests, 3
  infra tests and 8 e2e specs); budget for it rather than reaching for a nullable column with a
  default, which would let a fixture skip the field the feature is about.
- When a required field is added to a fixture builder, set it FROM the builder's own related field
  (`groupAtIssue: overrides.group ?? "RED"`), never a bare literal — a hard-coded `"RED"` beside a
  configurable `group` silently makes every non-RED fixture card-stale and breaks unrelated specs.
- A module whose rule widens gets RENAMED with it: `staleCounts.ts` → `staleCard.ts` once the group
  joined the comparison. `git mv` first, then patch — two non-test importers and one i18n key is the
  whole cost, and a name that lies is read as one for five years.
- Both sides of a "what changed since" comparison take the SAME shape (`CardFacts = { counts,
  group }`), so neither can grow a field the other does not have.
- A use case that returns a derived aggregate reads it AFTER its write (`changeGroup` →
  `groupCounts()`), and the fake must actually count the holders — a stubbed `{ red: 0, blue: 0 }`
  proves only that a constant travels.
- "The change is in force immediately" is proved by driving the real downstream read at one instant:
  `lookupCustomer` gives `WRONG_GROUP` before `changeGroup` and `CLEAR_TO_SERVE` after, on the same
  fake clock. Same move as `updateHousehold`'s cards-due test.
- Week colours under `weekAnchor 2026-W02/RED`: 2026-07-29 (the suites' TODAY) is a **BLUE** week;
  2026-08-05 and 2026-07-22 are RED. A spec needing the other colour moves the clock, not the anchor.
- A no-op state change is an ERROR, not a quiet success, wherever the change writes an audit entry or
  makes something else stale (`GroupUnchanged`). Silently accepting it fills the log with moves that
  never happened.
- A new `DomainError` subclass also needs its `code` added to the `DomainErrorCode` union in
  errors.ts — typecheck catches it, lint does not. Its 100% coverage comes from the use-case test
  that raises it; there is no per-error test file.

- A React form with an `action` is **reset by React once the action resolves**, and a reset restores
  each field from its *attribute*, not from the property React set. Controlled text inputs and
  textareas survive it (React re-applies `value` on the next render); a controlled RADIO does not —
  it comes back on whatever was `checked` at SSR, silently disagreeing with the data beside it.
  Render radios in an action form as `defaultChecked={x === current}`: the reset then restores what
  the revalidated render wrote. Symptom: the control shows the old value while everything derived
  from the new one is correct.
- Turning a read-only list into an editable one BREAKS every e2e assertion that read a name off the
  page: `toContainText` cannot see an `<input value=…>`. Grep the specs for the values the section
  showed and move them to `toHaveValue` before running the suite.
- A screen with several independent forms gets ONE state union (`RecordFormState`) and one
  feedback/button/field module, not one per form — and its `saved` carries a COUNTER, so a `key` can
  remount a form after a save that changed nothing visible.
- An error translator shared by two screens must NOT own the fallback: `customerErrorMessage`
  returns `string | null` and each screen supplies its own last word ("Die Aufnahme konnte nicht
  gespeichert werden" vs "Die Änderung konnte nicht …"). The shared branches then cannot drift while
  the wording stays each screen's own.
- A page may call a SECOND read use case when the first cannot honestly supply the value
  (`readCurrentSettings` beside `readCustomer`, for the four per-head numbers a browser-side
  derivation needs). Check first that it adds no new failure mode — here `readCustomer` already
  throws `NoSettingsInForce`, so there is no extra branch to cover.
- Widening a domain function's parameter from `Settings` to a `Pick` (`priceFor` → `PriceValues`,
  mirroring `portionsFor`) is source-compatible with every existing caller and is what lets a client
  component hold only the values that bear on the answer.

- A rule that registration and a later EDIT must both obey belongs in its own exported domain
  function that registration then calls (`createHouseholdMembers` ← `createCustomerDetails`). The
  edit reusing it is the only thing that keeps the two from drifting; a second implementation is
  free to accept what registration refuses.
- "The consequence follows automatically" is provable in the application layer by driving the REAL
  downstream read over the same fake register — updateHousehold's test calls `listCardsDueForReissue`
  after the edit rather than asserting a flag. It proves the derivation, not the intent.
- An archived customer's record is read-only (US-16, FR-8): every new mutating use case must refuse
  with `CustomerArchived` and every one of them must still allow a BLOCKED customer, which pauses the
  counter and not the record.
- A duplicated fact that CANNOT be de-duplicated (the customer is their own household member) is
  kept in step by a **pure domain rule plus one transaction**, never by two writes or by the adapter
  comparing rows: `replaceHouseholdMember(members, was, becomes)` decides which row was them, and
  `updateDetails(id, details, household)` writes both halves at once. Match on the row's *old*
  values, take only the first match, and leave the set alone when nothing matches — guessing is how
  an edit rewrites somebody else. Write the reasoning down: the reader's first instinct is that the
  duplication is a bug.
- Two use cases that touch the same record still get **one file and one audit event each**. A merged
  `updateCustomer` would produce an entry naming every field on every save, which is a log nobody
  reads. `maintain-customer.test.ts` is the shared suite; its `household()` fixture now takes
  `firstName` / `lastName` / `notes`, and its default household's FIRST row is the customer, which is
  what a registration leaves behind.
- A criterion phrased as "X is visible at the counter" is proved by driving the real `lookupCustomer`
  over the same fake register, not by asserting the stored column — the same move as
  `updateHousehold`'s cards-due test. The price is three more fakes in the file (settings,
  distribution records, reminder log); they can all be stubs, since the point is the read path.
- An input type is the guarantee: `UpdateCustomerDetailsInput` has no `customerNumber` field, and the
  port method takes none either, so "the customer number is not editable" (US-16, FR-7) is enforced
  by the compiler rather than by a check somebody could delete.
