## Codebase Patterns
- Adding a method to a port interface (e.g. CustomerRepository) forces EVERY implementer to compile:
  the real Prisma adapter AND the hand-written fakes, which live in several test files —
  customers.test.ts, certificate-reminder.test.ts, lookup-customer.test.ts and
  distribution/record-attendance.test.ts. `grep -rln "implements <Port>" src/` before you start.
  Miss one and typecheck fails, not lint.
- Adding a field to RegisteredCustomer ripples the same way: every fake `create` returning
  `{ ...customer, id }` and every builder literal needs the new field.
- `issueCard` (application/customers/issue-card.ts) is the ONE path by which a card comes into
  existence; `reissueCard` delegates to it and only narrows the reason. Never write a second issuing
  path — validity is "holds the highest index", so a parallel path is how two valid cards appear.
- Prisma migrations are pre-release disposable, but ADDITIVE changes (a new nullable column) get
  their own migration via `npx prisma migrate dev --name <x> --skip-generate`, then
  `npx prisma generate`. Infra tests spin a throwaway DB with `prisma migrate deploy`, so only a
  committed migration makes them see the column.
- Status changes go through `transition(from, to, reason?)` in domain/customer/status.ts, never an
  ad-hoc status assignment; persist via CustomerRepository.setStatus.
- Derive-don't-store: household counts, ages, card validity and the card number are all derived on
  read (readCustomer / readCard / describeAllowance), never stored.
- German UI strings only in `src/i18n/de.ts`; inflected forms are functions in the dictionary.
- Coverage is gated at 100% on domain/ and application/ — any new branch needs a named test.
- e2e specs (tests/e2e/*.spec.ts) do not run under `npm run test:coverage`; run `npm run test:e2e`.
  Its webServer is `npm run start` (the BUILT app) with `reuseExistingServer`, so an app-layer change
  needs `npm run build` first or the browser sees old code.
- e2e specs seed straight through Prisma and navigate by the SURROGATE id (`/kunden/${id}`), not the
  customer number. Owned number ranges keep the shared data/e2e.db predictable: counter 201-206/239,
  portions 211, serve 221-222, reminders 231, block 241, reissue 251. Take the NEXT free range up;
  never a number the allocator would hand out, or the registration specs' assertions move.
- Assert that a refusal wrote NOTHING by bracketing it with one Prisma snapshot helper returning
  `JSON.stringify({ status, cards, records, auditEntries })` and comparing before/after, rather than
  asserting each field. One equality covers every table the screen could have touched, and a future
  write that nobody thought to check still fails the spec.
- Assert German UI text in e2e specs by importing `de` from `@/i18n/de` and calling the dictionary
  function (`de.customers.reissue.confirm(a, b)`), never by pasting the sentence. A reworded string
  then stays a one-file change instead of breaking specs.
- App-layer write screens follow one shape: a `"use server"` `actions.ts` (Zod-parse the hidden
  `customerId`, call ONE use case, map typed domain errors to German, `revalidatePath`), a
  `*-state.ts` holding the form-state type + initial value (a `"use server"` module may export only
  async functions), and a `"use client"` component using `useActionState`. `customerDeps` already
  bundles customers+cards+settings+clock+audit and satisfies most use-case Deps structurally.
- The customer record page is `/kunden/[id]` (page.tsx + block-controls.tsx); the card view is
  `/kunden/[id]/karte`. Extend them rather than adding pages.
- A count the UI shows belongs in the repository as an aggregate, not as a `.filter()` over a list
  the read model already holds: the filter is a second statement of the rule (which reason counts as
  a loss) and drifts the day a reason is added. `prisma.card.groupBy` with `_count`/`_max` is the
  shape — one round trip, constant cost.
- A number the confirmation text of a write screen has to name (the next card number, a computed
  total) belongs on the READ MODEL, not in the page: `app/` is thin and "the next index is the
  current one plus one" is a rule. Both readCustomer and readCard now carry `nextCardNumber`,
  derived through the domain's `nextCardNumber()` so the rule has one statement.
- One client control can serve two screens. `[id]/reissue-controls.tsx` is imported by both
  `[id]/page.tsx` and `[id]/karte/page.tsx`; its action `revalidatePath`s BOTH routes, so whichever
  screen was used shows the new state and the other one does when next opened.
- Reason/status/group words come out of SQLite as plain strings and are narrowed by a `parse*`
  function (`parseCardIssueReason`) that THROWS `InvalidCustomerRecord`. Do this in aggregates too —
  a bare `=== "LOST"` would let a hand-edited row silently vanish from a count.

  the superseded card still on record, two reissues in a row (→ index 3), ten in a row (→ index 11),

  `customer.card.issued` with `why: "LOST"`, blocked customer served, archived refused with nothing
  written.
- To state "the distribution history is unchanged" as behaviour rather than as a type-level fact, the
  test file gained a `FakeDistributionRecordRepository` with a `writes` counter that is handed to the
  use case in `deps()` even though `ReissueCardDeps` has no such port. A use case that ever grew a
  write to it fails the counter.
- Files changed: src/application/customers/reissue-card.ts (new),
  src/application/customers/customers.test.ts, docs/technical_documentation.md (module section +
  repo-layout tree), scripts/ralph/prd.json, scripts/ralph/progress.txt.
- Checks: lint, typecheck, test:coverage (522 tests, 33 files, 100% on domain/application incl. the
  new module), build — all green. No UI in this story, so no browser check applies.
- **Learnings for future iterations:**
  - `FakeCustomerRepository.findById` returns the customer as it was *created*, so the fake's
    `customer.card` does NOT follow a reissue — only the real adapter derives it from the highest
    card row (`cards: { orderBy: { index: "desc" }, take: 1 }` in CUSTOMER_INCLUDE). Assert a
    reissue's new index through `cards.currentCard`/`listCards`, never through `findById(...).card`,
    and don't `toEqual` the whole customer before/after.
  - `FakeCardRepository.place(customerId, ...indices)` seeds cards without going through a use case
    and always stamps them `FIRST_ISSUE` — US-002 needs a mixed-reason history, so it will want a
    reason parameter (or a second seeding helper) rather than a fresh fake.
  - Passing an object with extra properties to a narrower Deps parameter is fine as long as it comes
    from a function's return value (`reissueCard(deps(), …)`) — TypeScript's excess-property check
    only fires on a fresh object literal at the call site.
  - Next up, US-002 exposes `cardsIssued` (current index) and `reissuesForLoss` (count of LOST cards)
    on the customer read model. The criterion demands ONE aggregate query, so it wants a new
    `CardRepository` method (e.g. `issueCounts(customerId)`) backed by `prisma.card.count`/`groupBy`
    — not `listCards().filter(...)` in application code. Remember: adding to CardRepository means
    updating every `implements CardRepository` fake.

## 2026-07-26 - US-002 (reissue counts on the read model)
- `CardRepository` gained `issueCounts(customerId): Promise<CardIssueCounts>` with
  `{ cardsIssued, reissuesForLoss }` (new type in ports.ts). `cardsIssued` is the CURRENT INDEX, not
  the row count — the PRD defines it that way and a gap in the run must not shrink it.
- `PrismaCardRepository.issueCounts` is ONE `prisma.card.groupBy({ by: ["reason"], _count: {_all},
  _max: {index} })`, reduced in the adapter: highest index = largest group max, loss count = size of
  the LOST group. Constant cost whatever the length of the run (US-09.2 forbids load-all-and-count).
- `readCard`'s `CardView` now carries `cardsIssued` and `reissuesForLoss`. Read "the customer read
  model" as the CARD read model: US-09.3 puts the display on the card view, and `ReadCustomerDeps`
  has no `cards` port, so putting it on `readCustomer` would have meant a new dependency for a screen
  that does not show it. It calls the aggregate instead of filtering `superseded`.
- Tests: 4 in customers.test.ts (`readCard` describe) — first card = 1/0, three cards through two
  reissues, the mixed history keeping STALE_COUNTS out of the loss count, and ten losses reported
  without a warning; 6 in card-repository.test.ts — the PRD's FIRST_ISSUE/LOST/STALE_COUNTS/LOST
  history asserting 4 and 2, first card, no card, a gapped run, scoping to one customer, and a
  hand-edited reason refused.
- Files changed: src/application/ports.ts, src/application/customers/read-card.ts,
  src/application/customers/customers.test.ts, src/infrastructure/prisma/card-repository.ts,
  src/infrastructure/prisma/card-repository.test.ts, docs/technical_documentation.md (ports table,
  readCard section, card adapter section), scripts/ralph/prd.json, scripts/ralph/progress.txt.
- Checks: lint, typecheck, test:coverage (532 tests, 33 files, 100% on domain/application), build,
  prettier — all green. No UI in this story, so no browser check applies.
- **Learnings for future iterations:**
  - `FakeCardRepository` (customers.test.ts) is the ONLY `implements CardRepository` fake, so a port
    addition costs one file — unlike CustomerRepository, which has four.
  - The readCard tests seed reissues through `reissueCard(deps(), …)`; `cards.place()` still stamps
    everything FIRST_ISSUE, so it is useless for a reason-mixed history. Don't extend it — go through
    the use case, which is what the counts are meant to reflect anyway.
  - `groupBy` typing: `group._count._all` needs `_count: { _all: true }` (a bare `_count: true` types
    as a number and reads differently). `group._max.index` is `number | null` — coalesce it.
  - Prettier reformats markdown TABLES on `npm run format`; widening a cell rewrites every row of the
    table, which is noise in the diff but expected. Run `npm run format` before committing docs.
  - Next up, US-003 renders these on `/kunden/[id]/karte` plus a reissue action there and on
    `/kunden/[id]`, with a confirmation step naming the old and the next number. The next number is
    `cardsIssued + 1` — already on the view, so the page needs no extra query. All strings via
    src/i18n/de.ts; the action follows the actions.ts + *-state.ts + "use client" shape.
