## Codebase Patterns
- Adding a method to a port interface (e.g. CustomerRepository) forces EVERY implementer to compile:
  the real PrismaCustomerRepository AND the hand-written fakes, which live in FOUR test files —
  customers.test.ts, certificate-reminder.test.ts, lookup-customer.test.ts and
  distribution/record-attendance.test.ts. `grep -rln "implements CustomerRepository" src/` before
  you start. Miss one and typecheck fails, not lint.
- Adding a field to RegisteredCustomer ripples the same way: every fake `create` returning
  `{ ...customer, id }` and every `customerRecord()` builder literal needs the new field. It is on
  RegisteredCustomer, NOT NewCustomer (registration always produces ACTIVE / null blockReason).
- Prisma migrations are pre-release disposable but ADDITIVE changes (a new nullable column) just get
  their own migration via `npx prisma migrate dev --name <x> --skip-generate`; no need to regenerate
  init (which carries the hand-written partial unique index at its tail — regenerating drops it).
  Then `npx prisma generate` so the client types pick up the column. Infra tests spin up a throwaway
  DB with `prisma migrate deploy`, so a committed migration is what makes them see the column.
- Status changes go through `transition(from, to, reason?)` in domain/customer/status.ts, never an
  ad-hoc status assignment. It throws IllegalStatusTransition for illegal/no-op moves and
  MissingAuditReason for a reason-less `→ BLOCKED`. Persist via CustomerRepository.setStatus.
- The page at /kunden/[id] already exists (built in US-01 as the card landing). It renders
  `CustomerCardView` from `readCustomer` and links to the card view at /kunden/[id]/karte. Extend it
  rather than creating a new page.
- Derive-don't-store: age is a pure domain fn `ageInYears(birthDate, today)` in
  `src/domain/customer/householdComposition.ts`, sharing the anniversary/§188 BGB rollover convention
  with `composition`/`grownUpFrom` (29 Feb → 1 Mar in non-leap years). The application layer
  (`read-customer.ts`) derives ages via `deps.clock.now()` and hands them to the page ready to render.
- `RegisteredCustomer.reminderCount` already lives on the customer entity — the page reads
  `view.customer.reminderCount` directly, no application change needed.
- German UI strings only in `src/i18n/de.ts`. Inflected forms (e.g. "1 Jahr" vs "N Jahre") are
  functions in the dictionary, never in components.
- Coverage is gated at 100% on domain/ and application/. Any new branch needs a named boundary test.
- e2e specs (tests/e2e/*.spec.ts) are not run by `npm run test:coverage`; run `npm run test:e2e`
  separately. Existing registration.spec asserts household-member *count*, not text, so a rendered
  age suffix is safe.
- App-layer write screens follow one shape: a `"use server"` `actions.ts` (Zod-parse the hidden
  `customerId` via the `surrogateId` regex, call ONE use case, map typed domain errors to German,
  `revalidatePath("/<route>/<id>")`), a `*-state.ts` holding the form-state type+initial (a
  `"use server"` module may export only async functions), and a `"use client"` component using
  `useActionState`. `customerDeps` already bundles customers+cards+settings+clock+audit, so it
  satisfies most use-case Deps structurally with no new composition root.
- Block/unblock UI lives on `/kunden/[id]` (block-controls.tsx). Its Playwright testids: block-open,
  block-reason, block-submit, block-error, block-reason-current, unblock-open, unblock-submit. The
  counter verdict banner (ausgabe/counter-lookup.tsx) already renders a BLOCKED reason verbatim/in
  full — don't re-derive it on the record.

## 2026-07-25 - US-004 (Block fields and slot-occupancy invariant)
- The `blockReason String?` column and its migration were pulled forward in US-003, so this story is
  the two proof tests the PRD (§US-08.3) asks for — both in the SQLite integration suite.
- Invariant test (`PrismaCustomerRepository.setStatus`): drives one customer through
  block → unblock and block → archive, asserting `(blockReason !== null) === (status === "BLOCKED")`
  after every write. This also pins that `setStatus` *clears* a stale reason on unblock/archive, not
  just the status word — the write puts both columns in one statement, so they cannot disagree.
- Slot-occupancy tests (`the customer number slot constraint`): the active-number partial unique
  index refuses a BLOCKED row sharing an ACTIVE holder's number and refuses two BLOCKED rows on one
  number, while a BLOCKED and an ARCHIVED row may share a number — proving BLOCKED occupies the slot
  and only ARCHIVED is exempt, straight at the index rather than via the create/CustomerNumberTaken path.
- No production code change: the invariant is guaranteed by `transition()` (mandatory reason for
  → BLOCKED) plus the use cases, and `setStatus` is the sole mutation path. docs/technical_documentation.md
  already states the invariant ("blockReason non-null exactly when blocked"), so no doc change.
- Files changed: src/infrastructure/prisma/customer-repository.test.ts.
