## Codebase Patterns
- **Adding a `DomainErrorCode` is a three-file change**: the union in `src/domain/errors.ts`, the
  class beside it, and `TIERS` in `src/app/notice-tier.ts`. `TIERS` is a `Record` over the union, so
  the *build* fails until the code is tiered — that is the mechanism, not an obstacle. The header
  comment of `notice-tier.ts` counts the codes ("a 32nd code…", "the six red ones"), so it goes
  stale silently; update it with the entry.
- **The same mechanism guards `SettingsChange`**: its `switch` in `src/app/einstellungen/page.tsx`
  is exhaustive with no `default`, so adding a member to the union fails the build until the screen
  renders it. Do not silence it with a `default` branch.
- **An error class with no caller yet still needs a test**, because `domain/` coverage is gated at
  100%. `src/domain/errors.test.ts` is where those live — see the `MissingAuditReason` block for the
  shape, including the comment saying which story will call it.
- **`errors.ts` cannot import from `domain/card/`**: `cardNumber.ts` imports `errors.ts`, so a
  message that wants to read `66k1` writes the `k` inline rather than calling `formatCardNumber`.
- **Adding a field to `Settings` is a wide change before it is a deep one.** `createSettings` is
  called from the repository, the seed, the settings server action and every hand-written fake in
  the application tests; all of them must supply the new field before anything compiles. Land the
  field with a placeholder value at each call site, then replace them in the story that owns each.
  Get the *files* out of a wide break rather than the errors:
  `npm run typecheck 2>&1 | grep -E "^src/" | cut -d'(' -f1 | sort -u`.
- **A test that merely *uses* a field is not a test *of* it.** Several `settings.test.ts` cases
  reach for an arbitrary second field to prove the same-instant tie rule or the audit's changed-field
  list. When that field goes away, **re-point them**, do not delete them — deleting takes an
  unrelated rule with it and drops coverage below the gate.
- **A Prisma `P2002` cannot always name *which* constraint was broken.** `meta` is
  `{ modelName, target: [columns] }`, but where two unique indexes both cover the offending row
  SQLite reports only one of them, and not the one that was declared or created first. Where the
  distinction matters, match the target for the *shape* and then ask the database the question that
  actually distinguishes the two faults (`card-repository.ts`'s `issue` counts the customer's own
  rows on that index). For a **nested** write Prisma reports the *rooted* model — a card refused
  inside `customer.create` comes back as `modelName: "Customer"` — so the model name alone tells
  nothing about which table failed.
- **Regenerating `prisma/migrations/` drops the hand-written partial unique index** on
  `Customer.customerNumber` (`Customer_customerNumber_onRegister_key`) at the end of the migration
  SQL. `src/infrastructure/prisma/schema.test.ts` greps for it and for the `onDelete: Restrict`
  clauses, so a lost line fails CI rather than production — but re-add it deliberately. Three things
  batches 25–27 each had to learn:
  - **Delete `data/fd.db` before `migrate dev`**: with the old migration row still in
    `_prisma_migrations`, Prisma refuses to regenerate and writes nothing.
  - **Verify with `diff`, not by reading the new file**:
    `git show HEAD:prisma/migrations/<old>/migration.sql > /tmp/old.sql && diff /tmp/old.sql <new>`
    states in a few lines what the story is allowed to have changed. Anything else is a Prisma
    version drifting the DDL under you, which no gate would attribute to this commit.
  - **`migrate dev` applies the migration *before* the hand-written index is appended**, so the
    database it leaves does not have the index even though the committed SQL does. `npm run db:reset`
    afterwards is what makes the two agree — check with
    `SELECT sql FROM sqlite_master WHERE name='Customer_customerNumber_onRegister_key'` rather than
    trusting that the reset ran.
  - A regeneration **renames a directory that documents cite by name**. `grep -rn "<old-timestamp>_init"
    docs/ src/ tests/` afterwards; prefer the `prisma/migrations/*_init/migration.sql` glob, which
    survives the next one.
- **Never `pkill -f "next dev"`, and never `pkill -f "node.*next-server"`** — both patterns match the
  Bash tool's own wrapper command line and kill the shell (exit 144, no output). **And `ss` is not
  installed in this sandbox**, so `ss -ltnp | grep :3000 || echo free` reports "free" for every port,
  always: the `||` fires on `command not found`. (Batch 27's per-story notes recommend `ss` in two
  places — they are wrong; that is the bug this bullet exists to stop.) Check
  `ps aux | grep "[n]ext-server"` — the bracket keeps the pattern out of its own match — and
  `kill <pid>` by number.
- **A stale `next start` from an earlier iteration silently serves a mixed build.** The new
  `npm run start` fails with `EADDRINUSE` in the background while the page still renders, from the
  old server reading the *new* chunks off disk — a couple of console 500s are the only symptom.
  Check for a live server (`ps`, above) **before** trusting any browser check.
- **`npm run db:reset` does not reach a server that is already running.** It deletes `data/fd.db`,
  and SQLite keeps serving the running process from the deleted inode, so the screen goes on showing
  the pre-reset data. Restart the server after a reset, or the verification is of the old database.
  `db:seed` fills settings only — customers are not seeded, so a reset empties whatever manual
  clicking built up (the e2e suite makes its own registers).
- **Changing a seeded policy value moves e2e expectations.** `grep -rn ',00 €' tests/e2e/` before
  editing a number in `seed.ts`.

- **Choosing a number at the intake now starts with choosing the week.** `/kunden/neu` offers one
  parity at a time, so `selectOption("236")` finds no such option unless `#group-BLUE` is checked
  first — and the radio is controlled, so the check has to come after `hydrated()` or it moves the
  dot without moving the list. Same on the record's `number-change-select`. Six specs that used to

- **Two specs share the isolated register now** (`ISOLATED_SPECS`), `number-group` before
  `waiting-list`. Sharing is safe only because each empties it with `clearRegister` in its own
  `beforeAll` and sets the quota it needs in its first test — which they both have to do anyway, since
  a CI retry replays a `serial` block against the register the previous attempt filled. A spec needs
  that register when it has to **decide the quota**: since US-31 that includes making one *week* full
  while the register is not, which no quota on the shared register could ever reach.
- **e2e spec files run in alphabetical path order, one worker, one shared database.** So a spec that
  *writes* shared state is only ever seen by the files sorting after it — `npx playwright test --list`
  prints the order, and a **rename moves a spec in that order** (batch 27's `portions.spec.ts` →
  `allowance.spec.ts` moved it from the middle to second). Anything a spec asserts as an **absolute
  count of a shared thing** is therefore a landmine: `settings.spec.ts` counted its version history
  as `3` and `4` and read the seeded version as `nth(2)`. It now takes a baseline with
  `versionCount(page)` and asserts `before + 1`, and reads the oldest version as `.last()` — the same
  claim, stated so that it does not depend on who ran first.
- **Two consecutive saves on the settings screen need a `page.reload()` between them in e2e.** A
  successful save *clears* the form, and the revalidated render that does it can land **after** the
  next `fill`, rewinding the field to the stored value; the second save then appends a version that
  changed nothing and every history index below it shifts. **`selectOption` loses the race too** —
  this bullet used to say it survived, and batch 29 watched WebKit fail the Ausgabetag spec on that
  claim twice in a row. Reload and re-assert the stored value before touching the field again,
  whichever control it is.
- **The customer record renders two different household blocks.** `/kunden/<active>` gives the live

- **Prettier does not reflow comments.** Shortening a sentence inside a `/** */` block leaves a
  ragged short line that `prettier --check` happily accepts — and so does an over-wide one, though

  em dash is three bytes, `awk` counts it as three columns, and every sentence carrying one is
  reported as a violation it is not.
  `git diff -U0 | python3 -c "import sys; [print(len(l[1:-1]), l) for l in sys.stdin if l.startswith('+') and not l.startswith('+++') and len(l[1:-1]) > 100]"`
- **A `toEqual` on a *whole* record is the assertion a new field breaks, and `tsc` cannot see it.**
  Adding a required field to a domain type (`IssuedCard.customerNumber`, batch 30) leaves every
  `expect(x).toEqual({ …every field… })` typechecking and failing at run time with a one-line diff.
  The compiler finds the *constructors*; only the suite finds the assertions. Same family as the
  „renaming a Prisma column is not finished when `tsc` is green" bullet — run the tests even when
  the wide break looks closed.
- **A domain story that changes a signature is not domain-only.** Deleting an exported function or
  giving one a second argument breaks `app/`, `application/` and `infrastructure/` in the same
  commit, and those call sites are that story's own work — the tree has to be green at every
  iteration. Two rules keep it honest: change the *shape* only and never the behaviour, and write in
  a comment which later story deletes the line. Where a narrowing is still needed for one more
  iteration because a column still holds the old value, push it *down* into the adapter rather than
  keeping the domain function alive (batch 31's `parseStoredGroup` in `card-repository.ts`).
- **A required field added to a type a *writer* passes is a signal to split the type**, not to teach

  means the field belongs to the read model alone.

- **A controlled *radio* does not survive React's post-action `form.reset()`; a controlled text input
  does.** React keeps a controlled input's `defaultValue` attribute in step with its value and does
  **not** do the same for `defaultChecked`, so a reset restores the radio from the attribute the
  *server* rendered while the unchanged `checked` prop makes React repaint nothing — the dot rewinds
  and the state it is supposed to show does not. One line fixes it, on the input itself:
  `ref={(node) => { if (node !== null) node.defaultChecked = <the state>; }}`. Passing `checked` and
  `defaultChecked` together instead is a React warning, not a fix. No gate sees any of this: it is a
  browser check or nothing (batch 31, `/kunden/neu` and the record's number control). Assert
  `hasAttribute("checked")` and not only `.checked` — the attribute is what the reset restores from,
  so it is the half that tells a fixed control from one that happens to look right.

  fresh input mounts on the refused value whichever order React re-renders and resets in.
- **`whitespace-nowrap` on a `Stat` value is a narrow-screen bug, and the overflow check cannot see
  it.** A phrase („Offen 2,00 €") runs out through the *tile's* padding at 390px while
  `documentElement.scrollWidth - clientWidth` still reads `0` — the page does not overflow, the tile
  does. Pass the nowrap/width-floor pair only where two tiles exist to be diffed (§4); let a phrase
  wrap where they are not, and read the screenshot at 390 rather than the number.
- **A dictionary entry may not read `de` inside its own initialiser** — TypeScript makes the whole
  object implicitly `any` (TS7022) even though it would work at run time. Lift the shared clause to a
  module-level function above the object, which is what `eggRow`/`fromPersons` already are. Note also
  that `de.ts` is no longer import-free: `formatEuros` and `balanceKind` are imported so that money
  and the balance's wording are formatted in one place and no screen can print a leading minus.
- **`ui_styling_guide.md` §11's snippet still says `pkill -f next-server`, and that kills the Bash
  tool** (exit 144, no output) — the bullet above says why. Kill by pid from
  `ps aux | grep "[n]ext-server"`. And **driving the counter by hand needs `FD_FIXED_NOW_FILE` set on
  the server**, not just a seeded register: the demo day is deliberately not a distribution day, so no
  household is clear to serve. Pin a Thursday whose week colour matches the household (anchor
  `2026-W02` = RED, so odd week offsets are BLUE) and restart `npm run start` with it.
- **Renaming a Prisma column is not finished when `tsc` is green.** A `select: { paid: true }` in an
  e2e spec typechecks against the *generated client*, so `npm run typecheck` on `src/` passes while
  the suite would fail at run time — and five specs held one. After any column rename,
  `grep -rn "<oldColumn>" tests/e2e/ prisma/` and run **both** engines, not just Chromium.
- **A scripted fixture in `demo-seed.ts` must be exempted from the counted patterns, not layered on
  top of them.** `UNPAID_EVERY` and `NO_SHOW_EVERY` reach across the whole cast, so a household
  scripted to demonstrate one state ends on whatever the modulus left it with (batch 29's three
  balance households first came out at −12,00 €, −5,00 € and +1,00 €). Skip the pattern for the
  scripted shape while still incrementing its counter, so the rest of the register is unchanged —
  and verify the fixture by querying the seeded database, never by reading the script.
- **`/warteliste` has no free-slot count, and a move can never change one.** The waiting list names
  *one* free number and *one* applicant in a banner, and `/kunden` carries a boolean „Platz frei"
  badge — neither is a figure that can go up. „Noch N freie Nummern" lives on `/kunden/neu` and on
  the record's number control, and a household moving between slots swaps one taken number for
  another, so `|taken|` is invariant. Batch 30 wrote an AC asserting a count that rose on a screen
  that has none; assert the *composition* of the offer (the vacated number is offered, the taken one
  is not) rather than its size.
- **A partial unique index on an *expression* is how "at most one row in state X" is stated in
  SQLite**, and Prisma cannot express it: `CREATE UNIQUE INDEX "one_running_session" ON "T"("col" IS
  NOT NULL) WHERE <predicate>` hand-written at the end of the migration. Every row in the state
  indexes the same constant, so the second one collides. Two things follow that the column-based
  constraints in this repo do not prepare you for: **`P2002` names the index, not a column**, so the
  adapter matches `meta.target` on the index name; and the row that *won* is not in the error, so a
  refusal naming it costs one extra read (`distribution-session-repository.ts`).

- **A lost race is driven with a second real tab**, `page.context().newPage()` plus the same
  registration helper — not a hand-written Prisma row, which would skip the intake's own allocation
  and prove nothing about the refusal staff actually meet.

- **`tests/**` is inside `tsconfig`'s `include`, so a dictionary key cannot be deleted alone.**
  `npm run typecheck` covers `tests/e2e/*.spec.ts`, which read their expected text out of
  `src/i18n/de.ts` — removing a string breaks the typecheck until every spec quoting it goes too.
  Delete the German and the specs in one commit, or leave both and say which story takes them.
- **`prisma/demo-seed.ts` belongs to no story and breaks on every domain deletion.** It drives the
  real use cases, so it holds a call to almost all of them, and the
  `npm run typecheck 2>&1 | grep -E "^src/"` filter in the bullets above **hides it** — it is the
  one file outside `src/` that a wide domain change always reaches. Grep the raw typecheck output.
- **A second submit button on one screen is a screen defect, not a spec problem.** Playwright runs
  in strict mode, so a card that ends in a button already named on that page breaks every existing
  spec clicking the older one — and the temptation is `.first()`. Don't: `ui_styling_guide.md` §6
  and §9 already require distinct accessible names, and the German label is the one-line fix
  (US-33.7 found fifteen such call sites behind one duplicated „Speichern"). The *spec* breaking is
  the gate working.
- **A controlled `<select>` or radio inside a `useActionState` form needs its `default…` written by
  a `ref`.** React resets the form when the action resolves and a native reset reads the
  `selected`/`checked` **attribute**, which React never writes for a controlled control — so the
  value silently rewinds while the state says otherwise, on a save *and* on a refusal.
  `number-control.tsx` states the argument in full; `certificate-type-field.tsx` and
  `registration-form.tsx`'s group radio both carry the same three lines.

### Where batch 34 starts

The software derives everything about a distribution from the calendar: settings hold a week anchor
(„KW 02/2026 war Rot") and a distribution weekday, and from those follow the eligibility check at
the counter, the group tally, the no-show count and the correction window („nur am selben
Kalendertag"). **The real process does not follow the calendar** — DF merge the two groups for a
while, cancel a Thursday, hold an extra distribution — so from now on the basis is the
**Ausgabetermin that actually took place**: started by hand, given its group(s), ended by hand.

Requirements: `local_only/manually-start-ausgabe/refined-requirements.md` (A, B, D-3). Full PRD:
`tasks/prd-us-34-distribution-session.md`. **A and B ship together** — without A there is no session
for B's hand-outs to belong to, and without B a session is a row nothing reads — which makes this
the largest batch the project has run (12 stories).

What changes, in one line each:

- **At most one session runs at a time**, the same one on every workstation, and the software never
  ends one itself.
- „once per calendar day" becomes **„once per session"**, for hand-outs and for reminders.
- „correctable until midnight" becomes **„correctable until the session is ended"**; the most
  recently ended session can be **reopened** with a reason while no new one has started.
- „falsche Gruppe" is judged against the **running session's groups**, never against the parity of
  the calendar week.
- Ending writes **one** audit entry carrying the start and the end; a session **discarded** while
  empty writes **none at all**.

**Build order is inside-out and stories 1–6 must land before any screen story.**

**The three things most likely to go wrong:**

- **The re-added partial unique index** (story 3). This batch regenerates `prisma/migrations/` and
  adds a **second** hand-written index beside it — the one that makes SQLite refuse a second running
  session. The first symptom of the drift a missed index causes is the settings screen reporting
  that nothing is configured.
- **The guard order in `recordAttendance`** (story 5). US-32.5 documented why the once-per-day check
  comes *before* the verdict; the once-per-session check inherits that position. Reordered, a
  duplicate write is reported as an eligibility refusal and the counter reads the wrong sentence
  back. `CertificateControls` likewise derives `expired` from `lookupCustomer`'s own field and not
  from the verdict kind — that has to stay true now that `ALREADY_SERVED` outranks
  `CLEAR_TO_SERVE_CERTIFICATE_EXPIRED`.
- **The ten existing e2e specs that record a hand-out** (story 10) and now need a session started
  first. That is the batch's largest hidden cost, which is why it is a story of its own.

**Two port methods change name and shape in story 3** (`listForDay` → `listForSession`, `findOnDay`
→ `findInSession`), so every hand-written fake in `src/application/**/*.test.ts` gains them in that
story or nothing compiles.

**`getWeekColour` survives this batch with exactly one caller** — the Start screen's „nächste
Ausgabe" line. US-36 deletes it. A story that finds itself deleting `weekColour.ts` has picked up
the next batch's work, and `berlinDayKey` stays for the same reason: `noShows.ts` is still its
caller until US-36.

**This is one piece of work in four parts** — 34 → 35 → 36 → 37 — and **35 must not be deferred**:
every session ended before its freeze rule exists is lost to the detail view for good.

`docs/architecture/05-building-block-view.md`.

**Learnings for future iterations:**

- **`reopenDistributionSession` takes `{ sessionId, reason }`, not `{ reason }` as the PRD's
  shorthand writes it — deliberate, and US-34.8 must pass the id.** With no target there is no
  defensible error for „nothing has ever ended" (`DistributionSessionNotReopenable` carries a
  sessionId and no id exists), and `canReopen`'s first half — `mostRecentlyEnded?.id === session.id`
  — could only ever be tautologically true. The domain rule was built to *compare* a target against
  the most recent, and the PRD's own wording („unless **the target** is the most recently ended
  session") has no referent otherwise. It also settles the race the other reading loses: between the
  screen rendering the last ended session and the reason being saved, another workstation may have
  ended a newer one, and reopening *that* is not what anybody asked for. `lastEnded` carries the id
  the form needs (`read-distribution-session-state`), so the screen pays a hidden field for it.
- **Start and discard write NOTHING to the audit log, and both have a test that says so by name.**
  The rule is not „no entry for a small change" — it is that the log never shows a session that
  began and never ended, which is only true if the entry is written at the *end*, where it can name
  both instants at once. A later reader adding a `distribution.session.started` entry would break
  that without any gate noticing; the two named tests are the gate.
- **The guard order in `startDistributionSession` is the running session first, the group choice
  second.** Told the form is incomplete, a staff member fixes the form — when what is actually in
  their way is the afternoon somebody else has under way. `createSessionGroups` is therefore called
  *after* `findRunning`, inside the `sessions.start(…)` call.
- **A hand-written fake that stamps rather than deletes has to hide the stamp from its reads.** The
  first cut of `FakeDistributionSessionRepository` stored `DistributionSession & { discardedAt }` and
  handed the whole row back, so `toEqual` against a started session failed on an extra key. It now
  holds `{ discardedAt, session }` and returns `row.session` — which is also what the adapter does
  (`SessionRow` never leaves `distribution-session-repository.ts`). Worth copying for any port whose
  store filters rows out.
- **`SessionSummary.households` is `handouts.length`, not a count of distinct `customerId`s.**
  `@@unique([customerId, sessionId])` makes the two the same number, and re-deriving it in the use
  case would be a second answer to a question the database already settles.
- **Chapter 5's application table counts use cases and ports in its heading** („39 use cases behind
  eleven ports"), and nothing greps it. It is now „44 use cases behind twelve ports" — the twelfth
  port arrived with US-34.3 and the heading had not caught up. Check that line whenever a use case or
  a port is added.
- **No UI in this story, so no browser check was possible or needed.** `/ausgabe` still returns 500
  until US-34.7/34.8 build the start screen — unchanged from US-34.3, and still the inside-out build
  order working as planned.
