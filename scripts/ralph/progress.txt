## Codebase Patterns
(Carried forward by hand from the US-13 log — the archive rotation wipes this file, so the patterns
block has to be pasted into the fresh one. The other durable channel is the CLAUDE.md files.)
- Adding a method to a port interface (e.g. CustomerRepository) forces EVERY implementer to compile:
  the real Prisma adapter AND the hand-written fakes, which live in several test files —
  customers.test.ts, certificate-reminder.test.ts, lookup-customer.test.ts,
  cards-due-for-reissue.test.ts and distribution/record-attendance.test.ts.
  `grep -rln "implements <Port>" src/` before you start. Miss one and typecheck fails, not lint.
- Adding a field to RegisteredCustomer ripples the same way: every fake `create` returning
  `{ ...customer, id }` and every builder literal needs the new field.
- Adding a REQUIRED column to Customer ripples further still: ~12 fixtures write customer rows
  straight through Prisma (5 infra *-repository.test.ts + 7 tests/e2e/*.spec.ts). That is the price
  of a column the database will not default — and it is the point, because a fixture that skipped it
  would be a row the feature can never find. `grep -rn "prisma.customer.create" src tests`.
- `issueCard` (application/customers/issue-card.ts) is the ONE path by which a card comes into
  existence; `reissueCard` delegates to it and only narrows the reason. Never write a second issuing
  path — validity is "holds the highest index", so a parallel path is how two valid cards appear.
- Prisma migrations are pre-release disposable. `npx prisma migrate dev --name init` REGENERATES the
  single init migration and DROPS the hand-written partial unique index at its end — re-append it
  from the previous migration (`git show HEAD:prisma/migrations/<old>/migration.sql | tail -16`) or
  the slot rule is enforced by application code alone. `npm run db:reset` afterwards, and note that
  `migrate dev` refuses non-interactively if the dev db is ahead — delete data/fd.db first.
- Status changes go through `transition(from, to, reason?)` in domain/customer/status.ts, never an
  ad-hoc status assignment; persist via CustomerRepository.setStatus — except the archive, which has
  its own `archive(id, reason, archivedAt)` write because it stamps three columns and clears
  blockReason in one statement.
- Derive-don't-store: household counts, ages, card validity and the card number are all derived on
  read (readCustomer / readCard / describeAllowance), never stored. The only two exceptions are
  named in the root CLAUDE.md — the card's printed counts, and the folded name search keys.
- Narrowing a nullable pair that is non-null "exactly when status is X" belongs in the ADAPTER, not
  in the use case: define the narrowed type in ports.ts (e.g. `ArchivedCustomer extends
  RegisteredCustomer`) and let infrastructure refuse a hand-edited row with InvalidCustomerRecord.
  Doing it in application/ costs a defensive branch against the 100% coverage gate.
- Prisma defaults `onDelete` to `SetNull` for an OPTIONAL relation and `Restrict` for a required one,
  so every nullable relation must spell `onDelete: Restrict` out. schema.test.ts greps the schema for
  the words AND the migration SQL for `ON DELETE SET NULL` / `ON DELETE CASCADE`.
- A self-referencing FK (Customer.previousCustomerId) means "children first" is not enough to tear the
  register down: `clearRegister` nulls the links before `customer.deleteMany()`.
- SQLite reports a FK violation as P2003 with EMPTY `meta` — unlike P2002, the offending column cannot
  be read off the error, so attribution has to come from what the write itself contains.
- German UI strings only in `src/i18n/de.ts`; inflected forms are functions in the dictionary.
- The Edit tool struggles with strings containing umlauts/em-dashes; patch such lines with a small
  `python3 - <<'PY'` heredoc instead of fighting it.
- HTML forms do not nest: a panel with its own submit button on a screen that is already a form has
  to be a SIBLING, with the state they share lifted into a parent client component.
- A `key` change is the cheapest way to reset a form that mixes controlled and uncontrolled fields —
  remounting resets both kinds, and `useActionState`'s message with them.
- Convert a `Date` to `YYYY-MM-DD` on the SERVER before it reaches an `<input type="date">`; read in
  the browser's zone a midnight-UTC day lands on the day before. `germanDate` is for display only.
- A `key` remount is invisible to Playwright: after clicking something that applies a pre-fill, WAIT
  for the new form (a banner, a pre-filled value) before typing. A `fill` on the node about to be
  replaced is thrown away with it, and the submit then fails on a field the spec believes it filled.
- An e2e spec that has to prove "not this row" is strongest when the excluded row is *hard* to
  exclude: give the archived household and the active one the same surname, so only the status
  filter keeps them apart.
- `pkill -f "next start"` from the Bash tool kills the shell running it (the pattern matches the
  command line itself). Write `pkill -f "next[ ]start"`.

## 2026-07-27 09:00 — US-002 (draftFromArchived pre-fill)

- Implemented `draftFromArchived(deps, { archivedCustomerId })` in
  `src/application/customers/draft-from-archived.ts`: reads one archived record through
  `customers.findById` and returns a `RegistrationDraft` of the applicant's name, birthdate, address
  and household members — and nothing else. No clock, no audit log, no write of any kind.
- What is left out is the story: no customer number (freed the day they were archived, FR-3), no
  certificate (the paper the applicant holds today is a new one, FR-4), no group, card or reminder
  count, and no notes (PRD §5 excludes them from the carry-over). A test asserts the draft's exact
  key set, so a field that creeps in later has to be argued for.
- Every value is copied, `Date` instances included: a form writes back into what it binds to, and a
  shared `Date` is mutable, so the "editing the draft cannot alter the archived record" criterion is
  only true of a deep copy. The test mutates the draft every way a form can — overwriting fields via
  `Object.assign`, advancing dates with `setFullYear`, pushing a member — and asserts the stored row
  is unchanged.
- New domain error `CustomerNotArchived` (id + status): the archive search only lists archived rows,
  so an id for an ACTIVE or BLOCKED household came from elsewhere, and pre-filling from it would walk
  staff into registering a household that already holds a slot (FR-6).
- Files: `src/application/customers/draft-from-archived.ts` (new), `src/domain/errors.ts`,
  `src/application/customers/customers.test.ts` (new `draftFromArchived` describe, 7 tests),
  `docs/technical_documentation.md` (new section + the layout listing + the error list).
- Gates: lint, typecheck, `test:coverage` (670 tests, domain+application at 100%) and build all
  green. No UI in this story, so nothing to verify in the browser.

- **Learnings for future iterations:**
  - The draft deliberately does NOT carry `previousCustomerId`. US-003 must add the link itself —
    the obvious shape is an optional `previousCustomerId` on `RegisterCustomerInput`, passed by the
    screen from the archive match it already holds, plus the nullable self-referencing column.
  - Deps that a use case does not have are still worth passing in tests as **witnesses** (the
    `archiveCustomer` precedent, reused here): `deps()` returns an object with extra fields, and TS
    excess-property checking does not apply because the call site passes a variable rather than a
    fresh literal. That is how "creates nothing" becomes a behavioural assertion.
  - `Object.assign(draft.address, {...})` mutates through a `readonly` interface without a cast —
    handy for proving a returned value is a copy rather than a shared reference.
  - Prettier reformats long `await expect(...).rejects.toThrow(...)` chains; run
    `npx prettier --write` on the test file before `npm run lint` rather than after.

## 2026-07-27 09:10 — US-003 (re-registration through the existing registerCustomer path)

  `src/infrastructure/prisma/customer-repository.ts` (+ test), `src/infrastructure/prisma/schema.test.ts`,

- **Learnings for future iterations:**
  - **Prisma's default `onDelete` for an *optional* relation is `SetNull`, not `Restrict`.** The
    schema test only greps `schema.prisma` for the words, so an omitted action passes it while the
    generated SQL quietly nulls links on delete. Spell `onDelete: Restrict` out on every nullable
    relation; `schema.test.ts` now also greps the migration SQL for `ON DELETE SET NULL`.
  - A self-referencing FK breaks `clearRegister`: "children first" is not enough, because a customer
    row can restrict the delete of another customer row. It now runs

    predecessor link.
  - Adding a field to `NewCustomer` ripples to six builders (2 `NewCustomer`, 4 `RegisteredCustomer`
    literals across cards-due-for-reissue, certificate-reminder, lookup-customer and
    record-attendance). The fakes' `create` spreads `...customer`, so they need no change — only the
    literals do. `npm run typecheck` lists all of them in one pass; that is the cheapest way to find
    them.
  - US-004 (the UI) should pass `previousCustomerId` from the archive match the screen already holds,
    and must show the former number for recognition only — `formerCustomerNumber` on the search
    result, never the number about to be assigned.

## 2026-07-27 09:40 — US-004 (archive search and pre-fill UI on the registration screen)

- The registration screen gained an "Im Archiv suchen" panel above the form: last name, first name
  and date of birth, a result list showing name, birthdate, address, household size, archive date,
  the archive reason verbatim and the former customer number, and a "Daten übernehmen" button per
  row that fills the form from `draftFromArchived`.
- The panel is a **sibling** of the registration form, never nested in it — HTML forms do not nest,
  and the search criteria are not part of the registration that gets saved. `registration-screen.tsx`
  is the new client half holding the one thing the two share: which archived household was picked.
- The pre-fill is applied by **remounting the form under a new `key`**, not by writing into fields.
  The form keeps some values in `useState` and others as plain `defaultValue`s; a key change resets
  both in one move, and it is also exactly what "Übernahme verwerfen und leer beginnen" has to mean —
  no half-filled field left over from the household that was dropped.
- The "this is a new customer" statement is a banner between the panel and the form, so it is read
  before the form is: it names the household the data came from, the day they were archived and the
  number they held, and says a new number and a new card (k1) are being issued and the archived
  record stays untouched. In a result row the former number sits under a label that says *frühere*
  with the "freed at archiving, possibly someone else's by now" sentence directly beneath it.
- `previousCustomerId` travels from the picked match through a hidden input to `registerCustomer` —
  absent rather than blank for a walk-in, and validated in `actions.ts` as digits only, because the
  field is written by the screen and never typed.
- Files: `src/app/kunden/neu/registration-screen.tsx`, `archive-search-panel.tsx`,
  `archive-search-actions.ts`, `archive-search-state.ts` (all new), `registration-form.tsx`,
  `actions.ts`, `page.tsx`, `src/i18n/de.ts` (`customers.archiveSearch` grown from two strings to the
  whole panel), `docs/technical_documentation.md` (layout tree + four new presentation bullets).
- Gates: lint, typecheck, `test:coverage` (690 tests, domain+application still 100%), build and
  `test:e2e` (46 passed, no regression) all green. Verified in a real browser with a throwaway
  Playwright spec — search, the diacritic fold (typing `mueller` finds `Müller`), selection,
  pre-filled personal data / address / two household rows / derived counts, an edit of a pre-filled
  field, the clear control, the empty-query refusal and the no-match message. The spec was deleted
  afterwards because US-005 writes the durable one.

- **Learnings for future iterations:**
  - **A `key` change is the cheapest reset there is.** A form that mixes controlled and uncontrolled
    fields cannot be cleared field by field without turning every field controlled; remounting it
    resets both kinds and costs one `useState` counter. `useActionState`'s error message resets with
    it, which for a fresh pre-fill is what you want anyway.
  - **HTML forms do not nest.** Any panel with its own submit button that lives on a screen which is
    already a form has to be a sibling, with the shared state lifted into a parent client component.
    That is why `registration-screen.tsx` exists at all.
  - **Convert `Date` to `YYYY-MM-DD` on the server** before a value crosses to a client component
    that binds it to `<input type="date">`. Read in the browser's zone a midnight-UTC day lands on
    the day before for anyone west of Greenwich. `germanDate` (i18n/format.ts) is for display; the
    input needs the ISO day, and that helper lives in `archive-search-actions.ts`.
  - A `"use server"` module may export only async functions — so `PrefillDraft`, the state interface
    and the initial value all live in `archive-search-state.ts`, the same split every other screen
    here uses (`*-state.ts` beside `actions.ts`).
  - An imperative server-action call from a client component (`await loadArchivedDraft(id)` in an
    `onClick`) works fine and needs no `useActionState`; use `onClick={() => void select(match)}` for
    the floating promise. Track *which* row is loading (`loadingId`), not a global `pending` — with
    twenty rows a global flag hides which one was clicked.
  - Don't re-quote `MAX_ARCHIVE_SEARCH_RESULTS` in the UI: the "there are more" message takes the
    number actually on screen, `matches.length`. Derive, don't restate.
  - Playwright's browser locale renders `<input type="date">` as `mm/dd/yyyy`, but `.fill()` and
    `toHaveValue()` both speak ISO — assert `"1985-02-11"`, not what the screenshot shows.

## 2026-07-27 10:15 — US-005 (E2E: re-register a returning customer)

- New Playwright spec `tests/e2e/reregistration.spec.ts` (6 tests): a RED household is registered
  through the form, served on the pinned RED Thursday 08.01.2026, archived with a reason — and then
  the number they gave up is handed to the **next** registration, under the same surname and still
  active. Only then do they come back. That ordering is the story: a re-registration that tried to
  restore the old number would pass a friendlier fixture and collide here (FR-3).
- What it asserts: the archive search typed in CAPITALS finds them (the folded key decides, not the
  stored spelling) while the active namesake is absent (FR-6); the pre-fill carries personal data,
  address and both household rows with the counts derived again, and carries **no** certificate and
  no former number into the proposal; a pre-filled field can be edited and the whole pre-fill
  dropped back to a blank form; registering lands on a NEW record with a new number, `k1`, reminder
  count 0, no distribution history and `previousCustomerId` pointing at the predecessor (read from
  Prisma — no screen shows it). FR-5 is one equality: the predecessor's whole belongings snapshot
  (status, number, household, certificate, cards, hand-outs) taken before the re-registration reads
  it and compared afterwards, plus its one hand-out still there.
- Files: `tests/e2e/reregistration.spec.ts` (new), `docs/technical_documentation.md` (layout listing
  + the US-11 spec paragraph beside its neighbours).
- Gates: lint, typecheck, `test:coverage` (690 tests, domain+application still 100%), build and
  `test:e2e` (52 passed, 1 pre-existing skip) all green — the e2e run repeated against a freshly
  deleted and re-seeded `data/e2e.db`, not only against a reused server.

- **Learnings for future iterations:**
  - **The pre-fill remounts the form, and Playwright cannot see it coming.** The first version of the
    spec clicked "Daten übernehmen" and typed the certificate straight afterwards; the fill landed on
    the node React was about to replace, the certificate arrived empty and the save never redirected.
    A `selectMatch` helper now waits for the pre-fill banner before anything is typed. Any spec that
    types into a form after a `key` change needs that wait.
  - The exclusion assertion is only worth something if the excluded row is hard to exclude: both
    households here share a surname, so the ACTIVE one is kept out of the search by the status filter
    alone and nothing else.
  - `belongings()` is the third copy of the same snapshot idiom (counter, reissue, archive, now this
    one). Widen it with the schema: this version added `status`, `archiveReason`, `archivedAt` and
    `previousCustomerId`, because the snapshot is taken *after* archiving and the link must never be
    written backwards onto the predecessor.
  - The spec consumes two customer numbers net and leaves one archived record on the first, so it
    names no number of its own — every number is read off `proposed-number`, as its alphabetical
    neighbours do.
  - `pkill -f "next start"` in the Bash tool kills its own shell (the pattern matches the command
    line); `pkill -f "next[ ]start"` is the way to stop a reused Playwright web server so the next
    `npm run test:e2e` reseeds the database.
