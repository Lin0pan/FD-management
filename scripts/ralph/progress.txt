## Codebase Patterns
- **Adding a `DomainErrorCode` is a three-file change**: the union in `src/domain/errors.ts`, the
  class beside it, and `TIERS` in `src/app/notice-tier.ts`. `TIERS` is a `Record` over the union, so
  the *build* fails until the code is tiered — that is the mechanism, not an obstacle. The header
  comment of `notice-tier.ts` counts the codes ("a 32nd code…", "the six red ones"), so it goes
  stale silently; update it with the entry.
- **The same mechanism guards `SettingsChange`**: its `switch` in `src/app/einstellungen/page.tsx`
  is exhaustive with no `default`, so adding a member to the union fails the build until the screen
  renders it. Do not silence it with a `default` branch.
- **An error class with no caller yet still needs a test**, because `domain/` coverage is gated at
  100%. `src/domain/errors.test.ts` is where those live — see the `MissingAuditReason` block for the
  shape, including the comment saying which story will call it.
- **`errors.ts` cannot import from `domain/card/`**: `cardNumber.ts` imports `errors.ts`, so a
  message that wants to read `66k1` writes the `k` inline rather than calling `formatCardNumber`.
- **Adding a field to `Settings` is a wide change before it is a deep one.** `createSettings` is
  called from the repository, the seed, the settings server action and every hand-written fake in
  the application tests; all of them must supply the new field before anything compiles. Land the
  field with a placeholder value at each call site, then replace them in the story that owns each.
  Get the *files* out of a wide break rather than the errors:
  `npm run typecheck 2>&1 | grep -E "^src/" | cut -d'(' -f1 | sort -u`.
- **A test that merely *uses* a field is not a test *of* it.** Several `settings.test.ts` cases
  reach for an arbitrary second field to prove the same-instant tie rule or the audit's changed-field
  list. When that field goes away, **re-point them**, do not delete them — deleting takes an
  unrelated rule with it and drops coverage below the gate.
- **A Prisma `P2002` cannot always name *which* constraint was broken.** `meta` is
  `{ modelName, target: [columns] }`, but where two unique indexes both cover the offending row
  SQLite reports only one of them, and not the one that was declared or created first. Where the
  distinction matters, match the target for the *shape* and then ask the database the question that
  actually distinguishes the two faults (`card-repository.ts`'s `issue` counts the customer's own
  rows on that index). For a **nested** write Prisma reports the *rooted* model — a card refused
  inside `customer.create` comes back as `modelName: "Customer"` — so the model name alone tells
  nothing about which table failed.
- **Regenerating `prisma/migrations/` drops the hand-written partial unique index** on
  `Customer.customerNumber` (`Customer_customerNumber_onRegister_key`) at the end of the migration
  SQL. `src/infrastructure/prisma/schema.test.ts` greps for it and for the `onDelete: Restrict`
  clauses, so a lost line fails CI rather than production — but re-add it deliberately. Three things
  batches 25–27 each had to learn:
  - **Delete `data/fd.db` before `migrate dev`**: with the old migration row still in
    `_prisma_migrations`, Prisma refuses to regenerate and writes nothing.
  - **Verify with `diff`, not by reading the new file**:
    `git show HEAD:prisma/migrations/<old>/migration.sql > /tmp/old.sql && diff /tmp/old.sql <new>`
    states in a few lines what the story is allowed to have changed. Anything else is a Prisma
    version drifting the DDL under you, which no gate would attribute to this commit.
  - **`migrate dev` applies the migration *before* the hand-written index is appended**, so the
    database it leaves does not have the index even though the committed SQL does. `npm run db:reset`
    afterwards is what makes the two agree — check with
    `SELECT sql FROM sqlite_master WHERE name='Customer_customerNumber_onRegister_key'` rather than
    trusting that the reset ran.
  - A regeneration **renames a directory that documents cite by name**. `grep -rn "<old-timestamp>_init"
    docs/ src/ tests/` afterwards; prefer the `prisma/migrations/*_init/migration.sql` glob, which
    survives the next one.
- **Never `pkill -f "next dev"`, and never `pkill -f "node.*next-server"`** — both patterns match the
  Bash tool's own wrapper command line and kill the shell (exit 144, no output). **And `ss` is not
  installed in this sandbox**, so `ss -ltnp | grep :3000 || echo free` reports "free" for every port,
  always: the `||` fires on `command not found`. (Batch 27's per-story notes recommend `ss` in two
  places — they are wrong; that is the bug this bullet exists to stop.) Check
  `ps aux | grep "[n]ext-server"` — the bracket keeps the pattern out of its own match — and
  `kill <pid>` by number.
- **A stale `next start` from an earlier iteration silently serves a mixed build.** The new
  `npm run start` fails with `EADDRINUSE` in the background while the page still renders, from the
  old server reading the *new* chunks off disk — a couple of console 500s are the only symptom.
  Check for a live server (`ps`, above) **before** trusting any browser check.
- **`npm run db:reset` does not reach a server that is already running.** It deletes `data/fd.db`,
  and SQLite keeps serving the running process from the deleted inode, so the screen goes on showing
  the pre-reset data. Restart the server after a reset, or the verification is of the old database.
  `db:seed` fills settings only — customers are not seeded, so a reset empties whatever manual
  clicking built up (the e2e suite makes its own registers).
- **Changing a seeded policy value moves e2e expectations.** `grep -rn ',00 €' tests/e2e/` before
  editing a number in `seed.ts`.
- **The e2e customer-number bands, as they now stand.** Below the quota of 240: counter 201–206 and
  239, allowance 211, serve 221–222, reminders 231, registration 232–234, card numbers 236. Above it:
  block 241, reissue 251, age-13 271, customer-list 281–285, customer-record 291–293, group-progress
  301–303, group-walk 311–315, price cap 321, eggs 331–334, balance 341–344. A spec whose number must
  be **pickable in the /kunden/neu dropdown** has to sit below 240 — the pool is `1..quotaN` — and
  everything else should stay above it, clear of the low sequence the allocating specs (registration,
  card, archive, reregistration) consume. **A new spec takes a new band**; do not borrow another
  spec's numbers. **And a band above 315 must be seeded BLUE**: `group-walk.spec.ts` reads the whole
  shared register and asserts that the highest walkable RED number *is* its own 315, so one RED
  household seeded higher fails a spec the new one has no business in — `eggs` and `balance` are both
  BLUE for that reason and not by taste. **Below 240 the band may be RED**, which is what lets a spec
  reuse the RED distribution Thursday `2026-01-08` the reissue and card-number specs already pin —
  `number-change` (224–228) took that route because every number it drives has to be **pickable in a
  dropdown**: a slot moved onto, or a vacated slot handed to the next household, is offered from
  `1..quotaN`, so „a new band" and „inside the quota" are two rules and the second one wins. Sweep the
  numbers in use with `grep -rhno "\b2[0-9][0-9]\b" tests/e2e/*.spec.ts | cut -d: -f2 | sort -un`.
- **e2e spec files run in alphabetical path order, one worker, one shared database.** So a spec that
  *writes* shared state is only ever seen by the files sorting after it — `npx playwright test --list`
  prints the order, and a **rename moves a spec in that order** (batch 27's `portions.spec.ts` →
  `allowance.spec.ts` moved it from the middle to second). Anything a spec asserts as an **absolute
  count of a shared thing** is therefore a landmine: `settings.spec.ts` counted its version history
  as `3` and `4` and read the seeded version as `nth(2)`. It now takes a baseline with
  `versionCount(page)` and asserts `before + 1`, and reads the oldest version as `.last()` — the same
  claim, stated so that it does not depend on who ran first.
- **Two consecutive saves on the settings screen need a `page.reload()` between them in e2e.** A
  successful save *clears* the form, and the revalidated render that does it can land **after** the
  next `fill`, rewinding the field to the stored value; the second save then appends a version that
  changed nothing and every history index below it shifts. **`selectOption` loses the race too** —
  this bullet used to say it survived, and batch 29 watched WebKit fail the Ausgabetag spec on that
  claim twice in a row. Reload and re-assert the stored value before touching the field again,
  whichever control it is.
- **The customer record renders two different household blocks.** `/kunden/<active>` gives the live
  editor (`household-editor.tsx`), `/kunden/<archived>` gives `HouseholdReadOnly` in `[id]/page.tsx`.
  Both hold the same tiles, so a screen-level change has to be checked on one of each — **seed
  customer 6 is archived**.
- **Counts baked into prose go stale in files no story names, in both directions.** Removing two
  settings made "the ten fields of the settings form", "nine of the ten need no translation",
  "Seven of the nine settings", "printed only five of the eight settings" and a `toHaveLength(8)` all
  wrong at once; *adding* a field or a tile does the same. After any such change,
  `grep -rn "nine\|ten fields\|eight\|six tiles\|four figures" src/` — the suite catches only the
  assertion. The same applies to an **exported type you delete or rename**: `grep -rn "<TypeName>"`
  finds the `{@link}`-shaped references left behind in comments, which no gate sees.
- **Prettier does not reflow comments.** Shortening a sentence inside a `/** */` block leaves a
  ragged short line that `prettier --check` happily accepts — and so does an over-wide one, though
  the repo's width is 100. Re-wrap the paragraph by hand, and **measure with Python, not `awk`**: an
  em dash is three bytes, `awk` counts it as three columns, and every sentence carrying one is
  reported as a violation it is not.
  `git diff -U0 | python3 -c "import sys; [print(len(l[1:-1]), l) for l in sys.stdin if l.startswith('+') and not l.startswith('+++') and len(l[1:-1]) > 100]"`
- **A `toEqual` on a *whole* record is the assertion a new field breaks, and `tsc` cannot see it.**
  Adding a required field to a domain type (`IssuedCard.customerNumber`, batch 30) leaves every
  `expect(x).toEqual({ …every field… })` typechecking and failing at run time with a one-line diff.
  The compiler finds the *constructors*; only the suite finds the assertions. Same family as the
  „renaming a Prisma column is not finished when `tsc` is green" bullet — run the tests even when
  the wide break looks closed.
- **A domain story that changes a signature is not domain-only.** Deleting an exported function or
  giving one a second argument breaks `app/`, `application/` and `infrastructure/` in the same
  commit, and those call sites are that story's own work — the tree has to be green at every
  iteration. Two rules keep it honest: change the *shape* only and never the behaviour, and write in
  a comment which later story deletes the line. Where a narrowing is still needed for one more
  iteration because a column still holds the old value, push it *down* into the adapter rather than
  keeping the domain function alive (batch 31's `parseStoredGroup` in `card-repository.ts`).
- **A required field added to a type a *writer* passes is a signal to split the type**, not to teach
  every writer the new field. `NewCard = Omit<IssuedCard, "customerNumber">` and `NewCustomer.card:
  NewCard` kept the slot the store's to fill in — which is the actual invariant — and cut the fixture
  break from ~50 errors to 17 as a side effect. `RegisteredCustomer extends NewCustomer` then
  re-declares `card: IssuedCard`, which TypeScript allows because the stored shape is assignable to
  the written one. Look for that split whenever a "wide break" is mostly test fixtures: it usually
  means the field belongs to the read model alone.
- **Prettier owns every markdown table in `docs/`, and `npm run lint` does not check it.** `lint` is
  `eslint` alone; markdown formatting is `npm run format:check` (the pre-commit hook runs it). Widen
  one cell and Prettier re-flows every row of that table, so run `npx prettier --write` on the files
  you touched *before* reading the diff — otherwise you are reviewing a re-alignment.
- **Recording an ADR is four steps, and the script does one of them.**

  the intro paragraph above it then breaks the 100-column wrap — Prettier does not reflow prose, so
  re-wrap that sentence by hand after changing the counting word.
- **An ADR that corrects an older one is an amendment unless the whole decision fell.** ADR-016

- **`prettier --check` cannot parse `prisma/schema.prisma`** — „no parser could be inferred", so it
  is outside `npm run format:check` and nothing checks the width of a schema doc comment. Measure it

- **Never wrap a Markdown code span across two lines.** Prettier removes the continuation line's
  indentation, which silently breaks the list item around it — in root `CLAUDE.md` it dropped
  `` `card.index)` `` into column 0 inside a nested bullet. Keep the span on one line and rewrap the
  sentence.
- **A use case that already loads a customer's records must not load them twice.** `recordAttendance`

- **An unreachable `?? fallback` fails the 100% branch gate.** Where a lookup cannot miss (a row that

  answer that went nullable and one caller not ready for it — **move the expression to where a test
  already goes** instead: batch 31's `suggestGroup(...) ?? "RED"` sits above the allocation inside

- **A controlled field filled straight after a `goto` needs `fillSticky`, not `fill`** — including a
  `<textarea>`. Hydration re-renders it from the prop and the typed text comes back with the stored
  value spliced into it (`notes-field`, batch 29), which reads like a broken assertion rather than a
  race. `tests/e2e/day.ts` explains the window; the rule is the whole of it: plain `fill` only once
  the page has been interacted with, or on a field React does not own.
- **Before touching an e2e spec your story has no business in, `git stash` and run the suite on
  clean `HEAD`.** It is the only thing that separates a regression from this suite's WebKit
  flakiness. Note that a failure **aborts the files behind it** (`6 did not run`), so one flake hides
  whatever else would have failed — and a green run after a fix is worth repeating twice.
- **A controlled *radio* does not survive React's post-action `form.reset()`; a controlled text input
  does.** React keeps a controlled input's `defaultValue` attribute in step with its value and does
  **not** do the same for `defaultChecked`, so a reset restores the radio from the attribute the
  *server* rendered while the unchanged `checked` prop makes React repaint nothing — the dot rewinds
  and the state it is supposed to show does not. One line fixes it, on the input itself:
  `ref={(node) => { if (node !== null) node.defaultChecked = <the state>; }}`. Passing `checked` and
  `defaultChecked` together instead is a React warning, not a fix. No gate sees any of this: it is a
  browser check or nothing (batch 31, `/kunden/neu` and the record's number control). Assert
  `hasAttribute("checked")` and not only `.checked` — the attribute is what the reset restores from,
  so it is the half that tells a fixed control from one that happens to look right.
- **`list[0]` lies in this repo; `list.at(0) ?? fallback` does not.** `tsconfig` has no
  `noUncheckedIndexedAccess`, so an index access on a possibly-empty array types as present and the
  `?? fallback` beside it reads as dead code to the next reader. `.at(0)` returns `T | undefined`,
  which lets a chain of `??` state the fallbacks a value actually has without a `!` — see
  `number-control.tsx`'s pick → own slot → group's lowest.
- **Radios that must not be submitted simply have no `name`.** An unnamed control is left out of

  roving of a native group — Tab reaches each radio and Space picks it. That is how a control can be
  browser state inside a `<form>` without a field nobody reads (US-31.6).

  scripted to demonstrate one state ends on whatever the modulus left it with (batch 29's three
  balance households first came out at −12,00 €, −5,00 € and +1,00 €). Skip the pattern for the
  scripted shape while still incrementing its counter, so the rest of the register is unchanged —
  and verify the fixture by querying the seeded database, never by reading the script.
- **`/warteliste` has no free-slot count, and a move can never change one.** The waiting list names
  *one* free number and *one* applicant in a banner, and `/kunden` carries a boolean „Platz frei"
  badge — neither is a figure that can go up. „Noch N freie Nummern" lives on `/kunden/neu` and on
  the record's number control, and a household moving between slots swaps one taken number for
  another, so `|taken|` is invariant. Batch 30 wrote an AC asserting a count that rose on a screen
  that has none; assert the *composition* of the offer (the vacated number is offered, the taken one
  is not) rather than its size.
- **A lost race is driven with a second real tab**, `page.context().newPage()` plus the same
  registration helper — not a hand-written Prisma row, which would skip the intake's own allocation
  and prove nothing about the refusal staff actually meet.

- **`tests/**` is inside `tsconfig`'s `include`, so a dictionary key cannot be deleted alone.**
  `npm run typecheck` covers `tests/e2e/*.spec.ts`, which read their expected text out of
  `src/i18n/de.ts` — removing a string breaks the typecheck until every spec quoting it goes too.
  Delete the German and the specs in one commit, or leave both and say which story takes them.
- **`prisma/demo-seed.ts` belongs to no story and breaks on every domain deletion.** It drives the
  real use cases, so it holds a call to almost all of them, and the
  `npm run typecheck 2>&1 | grep -E "^src/"` filter in the bullets above **hides it** — it is the
  one file outside `src/` that a wide domain change always reaches. Grep the raw typecheck output.


### Where batch 31 starts

Batch 30 (a customer number may be changed) is **merged into `main`** — PR #127, squashed as
`c61a432`, with #129 and #130 following it. So a household may be moved between slots, every card
carries the slot it was printed under, `Card.customerNumber` is read as the card's number (ADR-016),
and `changeCustomerNumber` writes the move and the new card in one transaction. **This batch builds
directly on that transaction and adds no second one.**

**This batch makes DF's oldest rule the software's rule: even customer numbers are BLUE, odd ones are
RED.** The group stops being a fact about a household and becomes a consequence of the number, derived
at every read. Read `tasks/prd-us-31-number-decides-the-group.md` §Introduction before writing a
line; its worked 37 → 106 table is the specification, and §9 of
`local_only/number-group-relation/refined-requirements.md` is why no validation is added anywhere.

**Almost all of this batch is deletion.** Going: `Customer.group`, `Card.groupAtIssue`,
`@@index([group])`, `CustomerRepository.setGroup`, `CustomerRepository.groupCounts`,
`CustomerListQuery.group`, `NewCustomer.group`, `RegisterCustomerInput.group`, the `changeGroup` use
case and its whole test file, `GroupUnchanged`, `parseGroup`, the `GROUP_CHANGE` stale-card reason,
the `customer.groupChanged` audit event, `GroupControl` and `changeGroupAction`. If a story finds
itself *adding* a way to store a group, it has misread the PRD.

Eight hazards, all stated in `prd.json` and worth reading twice:

- **The migration history IS regenerated this time** — the exact opposite of batch 30's note. Two
  columns and an index are dropped, so the four regeneration traps in the patterns bullet above all
  apply: delete `data/fd.db` first, re-add the hand-written partial unique index deliberately, verify
  with `diff` against `git show HEAD:prisma/migrations/<old>/migration.sql`, `npm run db:reset`
  afterwards, and grep for the renamed directory. **Re-confirm before deleting anything that DF still
  holds no real data** (ADR-009); the moment they enter their first customer this story is wrong.
- **Removing `RegisteredCustomer.group` and `IssuedCard.groupAtIssue` breaks every fake and every
  fixture at once**, the same wide break `IssuedCard.customerNumber` levied in batch 30 — except
  inverted, so the compiler leads you to every reader rather than every writer. Story 2 owns it. Get
  the *files* out of the break rather than the errors:
  `npm run typecheck 2>&1 | grep -E "^src/" | cut -d'(' -f1 | sort -u`.
- **Two port methods are removed, so two rounds of fake-updating**, and `CustomerListQuery.group`
  goes with them. Every hand-written fake in `src/application/**` that answers `groupCounts()` or
  filters `list` by group has to lose the method, not stub it.
- **The group filter deliberately leaves SQL.** SQLite cannot express `% 2` in a `WHERE` clause, so
  `listCustomers` and `readGroupRoster` narrow with `groupOf` after the query. **Do not "fix" this
  with a stored parity column or an `IN (1,3,5,…)` list** — the first is the second recording of the
  one fact this batch exists to record once, the second is a second expression of parity that has to
  agree with `groupOf` for ever. The register is quota-bounded at ~240 rows and four users.
- **The e2e re-banding is the widest change in the batch, and it breaks a shared invariant.** A
  fixture may no longer choose a group, so every seeded household's group is now its number's parity.
  `group-walk.spec.ts` seeds 311–315 RED and asserts that its own **315 is the highest walkable RED**
  in the shared register — but 321 (price cap), 331/333 (eggs) and 341/343 (balance) all become RED
  under the rule. Re-band so each spec's households carry the parity they claim, update
  `tests/e2e/registers.ts` and the seeds with them, and re-run the sweep:
  `grep -rhno "\b[23][0-9][0-9]\b" tests/e2e/*.spec.ts | cut -d: -f2 | sort -un`. Both engines, one
  run each.
- **`GROUP_CHANGE` is impossible, not merely unhandled.** A household's current card is always the
  highest index on the slot they currently hold — registration prints on the slot they take, a reissue
  on the slot they hold, and a move prints inside the transaction that moves them — so a current card
  can never name another group. State that as a named test rather than leaving it implicit; two
  derivations rest on it.
- **US-20's folded group choice is reversed on purpose.** The fold went in because DF accept the
  proposal; it comes out because the group now *drives the number list beneath it* and a folded
  control cannot say „Blau ist voll". Say so in the file's comment, naming US-20, or the next reader
  will re-fold it.
- **A group can be full while the register is not**, and that is the one genuinely new fact on both
  screens. It is why the free-number figures become per-group, why a full group is shown unselectable
  with its reason rather than as an empty dropdown, and why the waiting list is still only for a
  register with **no** free number at all.

The last story **narrows a written decision rather than reversing one**: ADR-007's first exception
loses `Card.groupAtIssue`, ADR-008 gains that a slot now carries which week it collects in, and
ADR-016 gains that a card keeping its number keeps its group. That is ADR-017, plus the root
`CLAUDE.md`, three architecture chapters, and a superseded-by note at the top of the US-16 and US-20
PRDs — which are **annotated, never rewritten**, per the patterns block above.

## 2026-09-01 — US-003 (US-31.3): registration allocates inside a group (application)

- `proposeRegistration` reads the register **once** — `takenActiveNumbers()` alone — and derives the
  pool (`freeNumbers`), both group sizes (`countByGroup`), the recommendation (`suggestGroup`) and
  the number the form opens on (`inGroup(free, suggested)[0]`) from that one reading. The
  `groupCounts()` call and the `Promise.all` around it are gone. `suggestedGroup` is `Group | null`,
  absent exactly when `customerNumber` is.
- `registerCustomer` allocates the lowest free number **of the recommended group** via a new
  file-local `allocateInGroup`. The group is decided from the first reading and held in
  `allocatedGroup` for every retry, so a lost race moves to the next slot of the same parity rather
  than crossing to the other week. `RegisterCustomerInput.group` is removed; the doc comment carries
  §9's argument (one field for the pair, so there is nothing to validate).
- Tests first, in `customers.test.ts`: `puts an allocated household in the recommended group`,
  `writes no group anywhere`, `retries within the same group after losing a number`,
  `crosses to the other group only when the one it started in has run out`,
  `registers the household on the number staff chose`, and for the proposal
  `recommends the smaller group…`, `recommends the other group when the smaller one is full`,
  `opens on the lowest free number of the recommended group`,
  `offers the whole free pool, not only the recommendation's`,
  `reports a full register as no number and no recommendation`, `reads the register once`.
- Files: `propose-registration.ts`, `register-customer.ts`, `customers.test.ts`,
  `kunden/neu/actions.ts`, `warteliste/[entryId]/registrieren/actions.ts`,
  `kunden/neu/registration-input.ts`, `kunden/neu/registration-form.tsx`,
  `docs/architecture/06-runtime-view.md` (scenario 2 no longer reads „group counts" from the DB).
- Gates: `npm run lint`, `npm run typecheck`, `npm run test:coverage` (56 files, 1301 tests, domain
  and application both 100%) and `npm run build` all pass, plus `npx prettier --check .`.

- **Learnings for future iterations:**
  - **„The retry stays inside its parity" needs the group hoisted out of the loop, and the loop then
    needs a way out of a group that emptied.** `allocateInGroup(group, taken, quotaN)` falls back to
    `lowestFreeNumber` over the whole pool for the two cases that are really one — the group has no
    number to offer. `group === null` is the full register (`NoFreeCustomerNumber`, unchanged
    meaning); a *named* group with nothing left is only reachable on a retry, and refusing an
    applicant there while a slot stands empty is precisely what the waiting list exists to prevent.
    Both branches are covered by tests, which the 100% gate demands — an unreachable fallback would
    have failed it.
  - **A register of `[2, 5, 7]` is the fixture that tells the new rule from the old one**: RED holds
    two slots and BLUE one, so the recommendation is BLUE and the allocation is **4** while the
    lowest free number is **1**. Steal 4 and the parities level at two apiece, so a retry that
    re-decided the group would allocate 1 — which is exactly what the retry test asserts it does
    not. Any test that wants to prove „by group" needs the recommendation and `free[0]` to disagree,
    and they agree far more often than you would guess.
  - **„The smaller group is full" needs households parked ABOVE the quota**, because with an even
    quota a full BLUE means every even slot is taken, and BLUE is then never strictly smaller. A
    quota lowered to 4 with the register holding `[2, 4, 11, 13, 15]` is the shape: RED 3, BLUE 2,
    BLUE full inside the quota. That is a real state (US-14), not a contrived one.
  - **Two existing tests were asserting the old allocation and had to move**: „moves to the next free
    number when another registration won the race" became the parity-locked retry, and „re-reads the
    card run for the slot a lost race moved the registration to" moved its second archived holder
    from slot 2 to slot 3. When a batch changes an allocation rule, sweep the tests that assert a
    *number* rather than a property of one.
  - **`RegisterCustomerInput.group` cannot be removed without touching both registration actions**
    (`/kunden/neu` and `/warteliste/[entryId]/registrieren`) — an excess property in an object
    literal is a typecheck error, so the two `group: form.group` lines are this story's work even
    though the form and the schema are US-31.6's. `registration-input.ts` keeps its `group` schema
    with a comment naming the story that deletes it; the radios still post a field nobody reads for
    one iteration.
  - **A nullable `suggestedGroup` breaks the form in three places** (`GROUP_STYLES[…]`,
    `de.customers.groups[…]`, `useState`). The stopgap is one `?? "RED"` at the top of
    `registration-form.tsx` with a comment saying US-31.6 rebuilds the block — it is only ever
    rendered on a full register, where the alert and the disabled form are the real answer.
  - **Two e2e specs now assert the old rule and are US-31.8's to fix**: `archive.spec.ts` („the freed
    number is handed to the next household…", ~line 347) and `reregistration.spec.ts` („their number
    is handed to somebody else…", ~line 310) both expect `/kunden/neu` to open on the number the
    archived household gave up. It is now offered in the dropdown but preselected only if it belongs
    to the recommended group. The claim to keep is „the vacated number is offered again"; the
    preselection is not that claim.

  first: no `v*` release holds DF data, `data/fd.db` is seeded demo data, and ADR-009 draws the line
  at real data rather than at a tag.
- **`CustomerRepository.groupCounts` and `NewCustomer.group` are off the port and out of the
  adapter**; `toRegisteredCustomer` and `toCard` no longer select or parse either column; `create`,
  `issue` and `changeCustomerNumber` no longer write one. `CustomerListQuery.group` and the
  „every criterion is a WHERE clause" correction landed in US-31.4 already.
- **`prisma/demo-seed.ts` needed nothing** — US-31.3 had already turned its group move into
  `changeCustomerNumber` into the other parity, so a seeded register says what its numbers say.
  `prisma/seed.ts` seeds only the settings version; it has never written a customer.
- Two new thin integration tests, both asserting the *columns* rather than a value: „stores a
  household without a group — the number they hold is the whole of it" and „stores a card without a
  group — the slot it was printed under is the whole of it". „counts the register's active numbers

- Files: `prisma/schema.prisma`, `prisma/migrations/*_init/migration.sql`, `src/application/ports.ts`,

- Gates: `npm run lint`, `npm run typecheck`, `npm run test:coverage` (56 files, 1309 tests, domain

  pass.

- **Learnings for future iterations:**
  - **Assert a dropped column against `Object.keys(row)` from a raw `SELECT *`, never against a
    value.** The precedent was already in the file („stores no grown-up or children count"). While a
    column exists there is a row that can be hand-edited into disagreeing with the number beside it,
    whatever the adapter writes into it — so „the adapter writes BLUE" and „there is nowhere to write
    BLUE" are different claims, and only the second is what US-31.5 delivers. `PRAGMA index_list` is
    the same trick for the index.
  - **Removing a required column breaks every Prisma `create` in the test suites at once**, because
    the fixtures pass it as an object literal — 6 infra test files and 18 e2e specs here. Typecheck
    finds all of them, so the sweep is mechanical; what it does *not* find is a `where: { group: … }`,
    which is a valid query against a column that no longer exists only until typecheck runs. Two
    e2e helpers (`walkableRedNumbers`, `todaysGroup`) had to stop filtering in SQL and start filtering
    with `inGroup`/`groupOf` in JavaScript, the same move `readGroupRoster` made in US-31.4.
  - **`npx prisma generate` before the gates after a schema edit.** The client is generated code and
    a stale one typechecks against the *old* columns, so a green typecheck proves nothing until it
    has been regenerated. `npm run db:reset` then proves the regenerated migration actually applies.
  - **The e2e suite is deliberately left red for US-31.8, and one case names why:**
    `group-walk.spec.ts` seeds 311–315 and asserts the walk visits `first: 311`, `blocked: 312` and
    `last: 315` in a RED week — but 312 is even and therefore BLUE under the rule, and `otherGroup:
    314` is BLUE for the same reason it always was. Every seeded household needs re-banding to the
    parity its assertions claim; that is US-31.8's widest change and its criteria say so.
  - **What US-31.6 through .9 inherit:** the registration form still posts a `group` field nobody
    reads (`registration-input.ts:182`, `registration-form.tsx:819`) and `RegisterCustomerInput.group`
    still takes it; the customer list still has a `gruppe` filter param feeding a criterion that is
    now narrowed in JavaScript; and `docs/architecture/06-runtime-view.md:192`,
    `08-crosscutting-concepts.md:52` and `ADR-007`'s exceptions table still describe `groupAtIssue`
    as a stored column. All four are named in US-31.9's criteria; left alone rather than
    half-corrected.

## 2026-09-02 — US-006 (US-31.6): one choice at registration (presentation)

- **`Zuordnung` is one block now**: the group radios first, the number select beneath them, the
  per-group free figures under that. `GRID`/`FIELD_ROWS` are gone from that section — the two-column
  subgrid existed to keep two side-by-side controls on one baseline, and there is one column now.
  The select took `sm:w-32`, the width the record's control already uses for the same list.
- **US-20's `<details>` is removed**, deliberately and with the comment saying so: the group now
  drives the list beneath it and a folded control cannot say „In Rot ist keine Nummer mehr frei."
- **The radios carry no `name`** and post nothing; `registration-input.ts` lost its `group` schema,
  its `GROUPS` import and the `group: text("group")` line. The registration form's `FormData` was
  read in the browser to prove it: `…, memberBirthDate, customerNumber` and no group, on both
  screens that save this form.
- **The number list is `inGroup(freeNumbers, group)`**, filtered in the browser. Changing the radio
  resets `picked` to `null`, so the preselection falls to that group's lowest free number. A group
  with nothing to offer is `disabled` and described by a sentence beside it
  (`aria-describedby` → `#group-RED-full`); on a *full register* those reasons are suppressed,
  because the alert at the top and the disabled submit already say it.
- German: `assignment.freeNumbersByGroup` („Noch frei — Rot: 12, Blau: 3") and `assignment.groupFull`
  are new, `assignment.groupChoiceOverride` is deleted. `freeNumberCount` **stays** — the record's
  number control still uses it — and its doc comment now says which screen it belongs to.
- Files: `registration-form.tsx`, `registration-input.ts`, `src/i18n/de.ts`, and a doc-comment line
  in both registration actions.
- Gates: `npm run lint`, `npm run typecheck`, `npm run test:coverage` (56 files, 1309 tests, domain
  and application both 100%), `npm run build` and `npx prettier --check .` all pass. Driven in the
  browser against `npm run start` (Chromium and WebKit), accessibility snapshot read at both widths.

- **Learnings for future iterations:**
  - **A controlled radio does NOT survive React's post-action `form.reset()`, and a controlled text
    input does.** This is the bug the browser check found and no gate would have: after a refused
    save the dot rewound to the server's proposal while the *list* beneath it stayed filtered by the
    group staff had picked — React state was right, the DOM was not. The reason is that React keeps
    a controlled input's `defaultValue` attribute in step with its value, and does **not** do the
    same for `defaultChecked`; a reset then restores the radio from the attribute the server
    rendered, and the unchanged `checked` prop makes React repaint nothing. The fix is one line —
    `ref={(node) => { if (node !== null) node.defaultChecked = option === group; }}` — which makes
    the reset a no-op. Do not pass `checked` and `defaultChecked` together: React warns. Confirmed
    broken and then fixed in **both** engines; US-31.7's radios on the record will need it too.
  - **A radio group without a `name` is the way to have radios that are not a field.** An unnamed
    control is not submitted, which is exactly „the radios are browser state" — and mutual exclusion
    is React's `checked`, so nothing is lost but the arrow-key roving of a native group. Tab reaches
    each radio and Space picks it; both were driven in the browser. The form-level `guardEnter`
    already covers Enter on a radio (checked: it submits nothing).
  - **The quota cannot be lowered below the active register**, so „drive a group full" in the browser
    is: lower the quota to the active count (15 in the demo register), then register the one or two
    remaining slots through the form. `data/fd.db` then holds a quota of 15 that
    `npx tsx prisma/demo-seed.ts --reset` does **not** undo — it re-seeds customers, not settings.
    `npm run db:reset && npx tsx prisma/demo-seed.ts` is the pair that puts both back, and the server
    has to be restarted after it (the running process keeps serving the deleted inode).
  - **`playwright-cli open --browser=chrome` fails in this sandbox** (no Google Chrome at
    /opt/google/chrome); plain `playwright-cli open` uses the bundled Chromium. WebKit needs
    `playwright-cli install-browser webkit` once — worth it, since the reset bug above had to be
    proved on both engines.
  - **What US-31.8 inherits from this story:** six specs still open the deleted disclosure
    (`archive.spec.ts:116`, `number-change.spec.ts:227`, `card-number.spec.ts:132`, `card.spec.ts:60`,
    `registration.spec.ts:599`, `reregistration.spec.ts:137` — all `getByTestId("group-choice-open")`
    followed by a `#group-*` click, which now needs the click alone), and
    `number-change.spec.ts`'s `freeNumberCount(page)` helper reads `free-number-count` on
    `/kunden/neu`, which is `free-numbers-by-group` now and carries **two** figures — stripping the
    non-digits out of it would silently produce „123". The testid was renamed on purpose so the
    helper fails loudly rather than asserting a number that means nothing.
  - **New testids on this screen:** `group-proposal` (the „Vorschlag … · Aktuell …" line) and
    `free-numbers-by-group`. The radios and the „group is full" sentences are reached by **CSS id**
    (`#group-RED`, `#group-RED-full`) — the ids exist for `aria-describedby` anyway and the specs
    already use them, so a second name for the same element would be clutter.

## 2026-09-02 — US-007 (US-31.7): one choice on the record (presentation)

- **„Gruppe" and „Kundennummer" are one section**, „Gruppe und Kundennummer", in the position
  „Gruppe" held. `NumberControl` grew the group radios above its select, in the intake's shape: the
  week first, the numbers that week offers beneath it, the two sizes and the per-group free figures
  under those. `GroupControl` and `changeGroupAction` were already gone (US-31.2); what landed here
  is the merge and the wording.
- **The radios open on `groupOf(customerNumber)`** and filter `choices` by their own `group` — the
  field `NumberChoice` grew in US-31.4, so the browser never works parity out. Picking the other week
  moves the selection to that week's lowest choice, because the household's own number is never in
  it. A week with no choice at all is `disabled` and described by
  `assignment.groupFull` (`aria-describedby` → `#group-RED-full`); the household's **own** week can
  never be in that state, since their own slot is always one of its choices.
- **The confirmation and the receipt name all three values** — number, group, card — whether or not
  the parity changed: the group is printed on the physical card, so it is copied out by hand rather
  than reported. „Kundennummer geändert 6 → **5**; Gruppe **Rot**; neue Karte **5k2** ausgestellt."
- **The record's header badge pairs the two**: „Nr. 5 · Rot", tinted with `GROUP_STYLES`, which is
  where a staff member learns to read one off the other (R-27). The tile below still states the
  number alone and labelled — that is the figure they copy.
- Dictionary: `record.groupHeading`, `groupHint`, `groupSubmit` and `groupSizes` are **deleted**;
  `numberChange.heading` is „Gruppe und Kundennummer"; `confirm` and `saved` gained the group;
  `record.numberAndGroup` is new; `assignment.groupSizes` now serves both screens and
  `assignment.freeNumberCount` is gone with the single total it stated.
- An archived household reads the group and the number as two read-only `Field`s and gets no control.
- Files: `kunden/[id]/number-control.tsx`, `kunden/[id]/page.tsx`, `src/i18n/de.ts`,
  `kunden/neu/archive-search-state.ts` (a `{@link}`-shaped reference to the deleted control),
  `docs/handout/betriebsanleitung.md`, and the three e2e call sites the dictionary signatures broke.
- Gates: `npm run lint`, `npm run typecheck`, `npm run test:coverage` (56 files, 1309 tests, domain
  and application both 100%), `npm run build` and `npx prettier --check .` all pass. Driven against
  `npm run start` in **Chromium and WebKit**, accessibility snapshot read at 390 and 1280.

- **Learnings for future iterations:**
  - **The controlled-radio reset bug is real on this screen too, and the same one line fixes it.**
    Proved rather than assumed: with the quota lowered in a second tab the move is refused
    (`CustomerNumberOutOfRange`), React resets the form, and without
    `ref={(node) => { if (node !== null) node.defaultChecked = option === group; }}` the dot would
    rewind to the group the *server* rendered while the list stayed filtered by the one staff picked.
    Checked in both engines by reading `hasAttribute("checked")`, not only `.checked` — the
    attribute is the thing the reset restores from, so it is the thing worth asserting.
  - **A refusal that does not re-read leaves the free figures stale, and that is correct.** Only
    `CustomerNumberTaken` sends a fresh list back (`freshChoicesAfterRace`); after an out-of-range
    refusal the figures still describe the register as the page was rendered with it. Do not "fix"
    this by re-reading on every refusal — the tier is the message there, and the screen says to
    reload.
  - **Driving a group full needs the quota, not fifteen registrations.** In the demo register the
    active households hold 1–3, 5, 7–15, 17, 18, so a quota of **18** leaves only 4, 6 and 16 free —
    RED is full inside the quota while the register is not. `/kunden/20` (BLUE) then shows RED
    unselectable with its reason, and `/kunden/6` (RED) shows RED selectable with one option, their
    own. Restore with `npm run db:reset && npx tsx prisma/demo-seed.ts`, then restart the server.
  - **`.at(0) ?? null` is how a "lowest of this list" fallback is written here.** `tsconfig` has no
    `noUncheckedIndexedAccess`, so `list[0]` types as present and would hide an empty list; `.at(0)`
    returns `T | undefined` and the `??` chain then states the three fallbacks the control actually
    has (the pick, the household's own slot, the group's lowest) without a `!`.
  - **A dictionary signature change breaks e2e specs that no gate would otherwise run.** Adding the
    group to `numberChange.confirm`/`saved` broke three call sites in `number-change.spec.ts`; they
    were fixed with `de.customers.groups[groupOf(to)]` rather than a literal, so the spec cannot
    disagree with the rule. `customer-record.spec.ts` still drives the deleted group control in three
    tests (US-31.8's) — only its `record.groupSizes` reference was re-pointed to keep `tsc` green.
  - **What US-31.8 inherits from this story:** the record's free-number line is
    `free-numbers-by-group` (was `number-change-count`, one total) and the radios are reached by CSS
    id `#group-RED` / `#group-BLUE` as at registration — `getByTestId("group-RED")` no longer
    resolves. `group-sizes` and every `number-change-*` testid are unchanged, and
    `record-number-group` is new on the header badge.
  - **The handout is user documentation and this story made two of its sentences wrong** — the
    section name and „beide Zahlen". Corrected here; the wider check US-31.9's criteria ask for
    („any page that tells DF to change a group on its own") is still open, and the manual still says
    nothing about the even/odd rule itself.
