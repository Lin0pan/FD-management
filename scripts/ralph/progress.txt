## Codebase Patterns
- **Measuring a screen's height**: `next build` then `npm run start -- --port 3100` (pkill -f
  next-server first), then playwright-cli. `document.body.scrollHeight` is useless on a short page —
  the shell fills the viewport, so it reads 900 either way. Measure the **last `main > *` child's
  `getBoundingClientRect().bottom`**, and measure a *populated* screen too (`/ausgabe?nummer=1`).
- **playwright-cli in this sandbox**: `playwright-cli open` only — `--browser=chrome` fails, there is
  no Google Chrome at /opt/google/chrome. The skill-version warning banner is noise; ignore it. Use
  `--raw` and `tail -1` to get just the value out of `eval`.
- **A grep across `tests/` is part of removing a UI element**, not only `src/`. A spec in a
  *different* file, named after a different screen, can be the one driving the element you are
  removing.
- **The dev server on 3100 reads `data/fd.db`**; the e2e servers read `data/e2e.db` (3000) and
  `data/e2e-isolated.db` (3001). Playwright's config reuses an existing server outside CI, so kill
  any `next-server` before `npm run test:e2e` or the suite tests the previous build.
- **Never `pkill -f next-server` from the Bash tool** — the pattern matches the tool's own wrapper
  command line and kills the shell (exit 144, no output). `pgrep -f "port 3100" | xargs kill` does
  the same. Use `ps -eo pid,args | grep -E "next-serve[r]"` and `kill` the pid.
- **`getByRole("alert")` is never 0 in this app.** Next injects a client-side route announcer with
  `role="alert"` into every page — invisible in the SSR HTML, so `curl | grep` disagrees with
  Playwright. Assert the absence of an error with `page.locator('[data-slot="alert"]')`; every
  shadcn `ui/` primitive carries a `data-slot`.
- **`tsconfig.json` includes `tests/`**, so `npm run typecheck` type-checks the specs. Deleting a key
  from `src/i18n/de.ts` fails typecheck while any spec still reads it — the spec has to go first.
- **`docs/technical_documentation.md` documents the e2e suite test by test**, so changing a spec
  makes it stale and no gate can tell. Grep that file for the *spec file name* after touching a
  spec, and for the feature's vocabulary after removing a feature — it is 2,500 lines and describes
  the same thing from the layer's side, the screen's side and the suite's side.
- **A retracted requirement is struck through, marked and kept**, never deleted: `~~criterion~~`
  plus `[withdrawn]` and the reason, in both `docs/user_stories_mvp.md` and the story's PRD. Say
  what is *not* withdrawn too, or the next reader removes a parameter that still has callers.
