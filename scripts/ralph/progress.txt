## Codebase Patterns
- **Adding a `DomainErrorCode` is a three-file change**: the union in `src/domain/errors.ts`, the
  class beside it, and `TIERS` in `src/app/notice-tier.ts`. `TIERS` is a `Record` over the union, so
  the *build* fails until the code is tiered — that is the mechanism, not an obstacle. The header
  comment of `notice-tier.ts` counts the codes ("a 32nd code…", "the six red ones"), so it goes
  stale silently; update it with the entry.
- **An error class with no caller yet still needs a test**, because `domain/` coverage is gated at
  100%. `src/domain/errors.test.ts` is where those live — see the `MissingAuditReason` block for the
  shape, including the comment saying which story will call it.
- **`errors.ts` cannot import from `domain/card/`**: `cardNumber.ts` imports `errors.ts`, so a
  message that wants to read `66k1` writes the `k` inline rather than calling `formatCardNumber`.
- **`docs/technical_documentation.md` explains each domain module in a `### <path>` section** and
  lists the error classes by name in the `src/domain/errors.ts` section. Adding an export or an
  error makes both stale and no gate can tell — grep the file for the module path *and* for the
  vocabulary of the rule being changed.
- **A Prisma `P2002` cannot always name *which* constraint was broken.** `meta` is
  `{ modelName, target: [columns] }`, but where two unique indexes both cover the offending row
  SQLite reports only one of them, and not the one that was declared or created first. Where the
  distinction matters, match the target for the *shape* and then ask the database the question that
  actually distinguishes the two faults (`card-repository.ts`'s `issue` counts the customer's own
  rows on that index). For a **nested** write Prisma reports the *rooted* model — a card refused
  inside `customer.create` comes back as `modelName: "Customer"` — so the model name alone tells
  nothing about which table failed.
- **Prior runs' patterns are in the archive**, not in this file: `scripts/ralph/archive/<date>-<story>/progress.txt`
  keeps a long consolidated list (playwright-cli usage, e2e customer-number bands, killing the dev
  server safely, testid greps). Read the most recent one before any UI or e2e story.

- **Learnings for future iterations:**
  - **`pkill -f next-server` kills the bash tool's own shell** (its command line contains the
    pattern), so everything after it in the command silently never runs — the call just exits 144.
    Use `pkill -f "next-serve[r]"` or `pgrep -f "next-serve[r]"` to check first.
  - **Prisma P2002 `meta` is `{ modelName, target: [columns] }`** on SQLite — e.g.
    `{"modelName":"Card","target":["customerNumber","index"]}`. So a collision check can and should
    name the model *and* the columns; `JSON.stringify(meta).includes("…")` matches across models and
    is what made a duplicate card number report itself as a taken customer number. US-003's split of
    `isCardIndexCollision` has the same shape: `target` is `["customerId","index"]` vs
    `["customerNumber","index"]`.
  - `prisma migrate dev` refuses to run while `data/fd.db` holds a migration that is no longer on
    disk: delete the db file first (the `db:reset` node one-liner does it), then regenerate.
  - `customer-repository.test.ts` now has `nextOnTheSlot(...)`, a `newCustomer` whose card index is
    one higher — any adapter test that registers a *second* household on one slot needs it, because
    two k1s on a number no longer fit through the database.
  - `card.spec.ts`'s title "a registration issues card k1" is only true on a slot nobody has held.
    It passes in isolation and fails in the suite, where an earlier spec has archived a household on
    slot 1. US-006 should decide whether the title still says what it means.

- **Learnings for future iterations:**
  - **The `isCardIndexCollision` split the PRD asks for cannot be done on the constraint target
    alone.** A card's `customerNumber` is written from the customer row, so a second card on an index
    the customer already holds violates `(customerId, index)` *and* `(customerNumber, index)`, and
    SQLite reports `["customerNumber","index"]` — even though `Card_customerId_index_key` is created
    first in the migration. `issue` therefore matches either of `Card`'s targets and then counts the
    customer's own rows on that index to decide which error it is. Do not "simplify" that back to a
    target match: the existing US-02.3 concurrency tests go red immediately.
  - **`PrismaCustomerRepository.create` had been mapping a duplicate *card* number to
    `CustomerNumberTaken`.** Prisma reports a nested write under the rooted model, so the modelName
    check US-002 added does not catch it; the columns do (`["customerNumber"]` = the register's
    partial index, `["customerNumber","index"]` = `Card`'s). US-004 needs this, because a
    registration writes its first card through `create` and not through `cards.issue`.
  - `FakeCardRepository` in `customers.test.ts` is now constructed with the customer register —
    `new FakeCardRepository(customers)` — because a card's slot is read off the customer row rather
    than passed in. Every `beforeEach` already built `customers` first.
  - The fake's `issueCounts` counts rows now too. No application test asserted the old max-index
    reading, so nothing outside infrastructure moved.
