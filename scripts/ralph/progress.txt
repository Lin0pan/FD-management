## Codebase Patterns
- Adding a method to a port interface (e.g. CustomerRepository) forces EVERY implementer to compile:
  the real PrismaCustomerRepository AND the hand-written fakes, which live in FOUR test files —
  customers.test.ts, certificate-reminder.test.ts, lookup-customer.test.ts and
  distribution/record-attendance.test.ts. `grep -rln "implements CustomerRepository" src/` before
  you start. Miss one and typecheck fails, not lint.
- Adding a field to RegisteredCustomer ripples the same way: every fake `create` returning
  `{ ...customer, id }` and every `customerRecord()` builder literal needs the new field. It is on
  RegisteredCustomer, NOT NewCustomer (registration always produces ACTIVE / null blockReason).
- Prisma migrations are pre-release disposable but ADDITIVE changes (a new nullable column) just get
  their own migration via `npx prisma migrate dev --name <x> --skip-generate`; no need to regenerate
  init (which carries the hand-written partial unique index at its tail — regenerating drops it).
  Then `npx prisma generate` so the client types pick up the column. Infra tests spin up a throwaway
  DB with `prisma migrate deploy`, so a committed migration is what makes them see the column.
- Status changes go through `transition(from, to, reason?)` in domain/customer/status.ts, never an
  ad-hoc status assignment. It throws IllegalStatusTransition for illegal/no-op moves and
  MissingAuditReason for a reason-less `→ BLOCKED`. Persist via CustomerRepository.setStatus.
- The page at /kunden/[id] already exists (built in US-01 as the card landing). It renders
  `CustomerCardView` from `readCustomer` and links to the card view at /kunden/[id]/karte. Extend it
  rather than creating a new page.
- Derive-don't-store: age is a pure domain fn `ageInYears(birthDate, today)` in
  `src/domain/customer/householdComposition.ts`, sharing the anniversary/§188 BGB rollover convention
  with `composition`/`grownUpFrom` (29 Feb → 1 Mar in non-leap years). The application layer
  (`read-customer.ts`) derives ages via `deps.clock.now()` and hands them to the page ready to render.
- `RegisteredCustomer.reminderCount` already lives on the customer entity — the page reads
  `view.customer.reminderCount` directly, no application change needed.
- German UI strings only in `src/i18n/de.ts`. Inflected forms (e.g. "1 Jahr" vs "N Jahre") are
  functions in the dictionary, never in components.
- Coverage is gated at 100% on domain/ and application/. Any new branch needs a named boundary test.
- e2e specs (tests/e2e/*.spec.ts) are not run by `npm run test:coverage`; run `npm run test:e2e`
  separately. Existing registration.spec asserts household-member *count*, not text, so a rendered
  age suffix is safe.

## 2026-07-25 - US-002 (Customer status transition state machine)
- Added `src/domain/customer/status.ts`: `transition(from, to, reason?)` returning the target for the
  four allowed moves (ACTIVE→BLOCKED, BLOCKED→ACTIVE, ACTIVE→ARCHIVED, BLOCKED→ARCHIVED) and throwing
  otherwise. `Status` is a type alias of the existing `CustomerStatus` from customer.ts — single
  source of truth, not a second enum.
- New typed `IllegalStatusTransition` error in errors.ts (carries `from`/`to`) for any move out of
  ARCHIVED and every no-op. A reason-less `→ BLOCKED` reuses the existing
  `MissingAuditReason("customer.blocked")`, not a new class (per PRD §US-08.1).
- Tests cover all 9 ordered pairs plus the empty/whitespace/undefined-reason branches.
- Files changed: src/domain/customer/status.ts (+test), src/domain/errors.ts.
- Checks: lint, typecheck, test:coverage (491 tests, 100% on pure layers), build all green.
- **Learnings for future iterations:**
  - `CustomerStatus` and `parseCustomerStatus` already live in `customer.ts`; don't redefine the enum
    in status.ts — alias it. US-004 will need the `blockReason` Prisma field + invariant, and US-003
    the blockCustomer/unblockCustomer use cases that call `transition`.
  - Adding a domain error = add the string to the `DomainErrorCode` union AND the class; coverage on
    errors.ts is gated at 100%, so every new error must be exercised by a test (status.test.ts does).

## 2026-07-25 - US-003 (blockCustomer and unblockCustomer use cases)
- Added `blockCustomer(deps, {customerId, reason})` and `unblockCustomer(deps, {customerId})` in
  src/application/customers/. Both load the customer, run `transition(...)` (the state machine owns
  legality + the mandatory-reason rule), persist via a new port method, and append one audit entry.
  Block trims the reason and stores it; unblock reads the reason first, clears it, and records the
  lifted reason as the audit `why` (the log is the only place a block's text survives once cleared).
- New port `CustomerRepository.setStatus(id, status, blockReason)`: one write of status + reason so
  they can never disagree. Implemented in PrismaCustomerRepository (`prisma.customer.update`).
- Added `blockReason: string | null` to `RegisteredCustomer` and the `blockReason String?` column to
  the Prisma Customer model + migration `20260724235102_customer_block_reason`. This was nominally
  US-004's migration, pulled forward because a port method must compile against real infra and a
  stored reason needs a column. US-004 keeps the invariant test + slot-occupancy integration test.
- Fake CustomerRepository (customers.test.ts) `takenActiveNumbers` now derives from live status
  (ACTIVE|BLOCKED occupy, ARCHIVED frees), which is what makes "a block does not free the slot"
  testable; `create` stopped pushing to `taken` (competitor steals still do). Added `setStatus` and
  `blockReason: null` to all four CustomerRepository fakes.
- Files: src/application/customers/{block-customer,unblock-customer}.ts (+customers.test.ts),
  src/application/ports.ts, src/domain/customer/customer.ts,
  src/infrastructure/prisma/customer-repository.ts, prisma/schema.prisma + migration,

  src/application/distribution/record-attendance.test.ts, docs/technical_documentation.md.
