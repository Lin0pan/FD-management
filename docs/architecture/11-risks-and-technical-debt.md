# 11. Risks and technical debt

_Last reviewed: 2026-08-07_

A **risk** might happen and is managed by mitigation and monitoring. **Debt** is a shortcut already
taken, paid for in every future change. Owner is "the maintainer" throughout, because there is one —
which is itself the third risk below.

## Risks

| Risk                                                                                                                                                                                                                                                               | Impact                                                                                  | Likelihood                                              | Mitigation / early warning                                                                                                                                                                           | Owner               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| **No backup exists.** `data/fd.db` is the whole system state and nothing copies it. No schedule, no destination, no restore drill                                                                                                                                  | **Total, irreversible.** A disk failure loses the register with no way back             | Medium over five years — it is a laptop                 | Define a schedule and destination _before go-live_, then perform one restore drill and record the date. Until that has happened, [scenario Q6](10-quality-requirements.md#scenarios) is a hypothesis | The maintainer + FD |
| **The migration-history switch is a human judgement.** [ADR-009](adr/009-regenerate-migration-history-until-fd-holds-real-data.md) reverses on the day FD enters their first real customer. If that day passes unnoticed, the next regeneration destroys real data | Total loss of live data                                                                 | Medium — the trigger is an event nobody is watching for | Make the reversal part of the go-live checklist, not a rule to remember. Early warning: any `prisma migrate dev --name init` after go-live                                                           | The maintainer      |
| **The hand-written partial unique index is dropped by every migration regeneration.** Without it, the one-household-per-number rule rests on application code alone                                                                                                | Two households on one customer number; the quota stops meaning anything                 | Medium while pre-release regeneration is normal         | `src/infrastructure/prisma/schema.test.ts` greps the generated SQL. That test is the early warning and must never be weakened                                                                        | The maintainer      |
| **The Excel migration is unanswered.** Import script or re-key ~240 households by hand — undecided                                                                                                                                                                 | Blocks go-live; a hand re-key is days of work and a fresh source of typos               | Certain to be faced                                     | Decide before scheduling go-live. Note it also decides _when_ the ADR-009 switch flips                                                                                                               | FD + the maintainer |
| **Single-developer key-person risk.** One person holds the design in their head                                                                                                                                                                                    | A handover without these documents would be expensive; with them it is merely hard      | Certain over a five-year horizon                        | This documentation set is the mitigation. Keeping it true is the ongoing cost — see the README's "keeping it current" note                                                                           | The maintainer      |
| **A shared, possibly unlocked machine is the entire access control.** [ADR-003](adr/003-ship-without-login-and-bind-the-application-to-localhost.md) accepts this consciously                                                                                      | Anyone with physical access reads or edits the register                                 | Depends entirely on FD's practice                       | Screen lock and machine placement — an operational control, not a software one. Revisit the ADR if FD ever wants the register on a second machine                                                    | FD                  |
| **The pinned Next.js major goes stale.** [ADR-004](adr/004-pin-the-next-js-major-and-keep-the-core-outside-the-framework.md) buys stability at the price of a growing jump                                                                                         | An eventual upgrade touching `src/app/` wholesale, or running on an unsupported version | Certain, on a multi-year timescale                      | The layering means the blast radius is `src/app/` only. Early warning: the pinned major leaving security support                                                                                     | The maintainer      |
| **The counter has no offline story if the machine itself fails mid-distribution**                                                                                                                                                                                  | A distribution afternoon runs on paper and is entered afterwards                        | Low                                                     | Accepted. Recording a hand-out after the fact is a normal write; nothing prevents it                                                                                                                 | FD                  |

## Review cadence

This chapter is worth nothing if it is written once. Re-read it whenever an ADR is added, and in full
before go-live — at which point the backup risk and the migration-switch risk stop being risks and
become either resolved or realised.
